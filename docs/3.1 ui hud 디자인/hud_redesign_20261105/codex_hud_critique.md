# H3 HUD A/B 독립 비평 — 2026-11-05

**수치·코드 기준, 화면 미검수.** Mac 캡처 없이 디자인 PASS·본선 채택을 판정하지 않는다. H1을 구현한 쪽의 재검토이며, 자체 테스트 통과를 시안의 품질이나 U1과의 픽셀 일치 증거로 쓰지 않았다.

## 4. 연구 규칙 자체의 약점

1. **근거 강도:** 검색 요약2곳 일치는 독립 원문2개 검증과 다르다. 같은2020 공식 글을 여러 매체가 재보도할 수 있다. 시대·플랫폼·상태가 다른 자료를 단일 HUD 명세로 합치지 않는다. 다른 게임 공통 관례 대조도 남았다(02_hud_ui.md:11–16,203–206,214–244; G0_BRIEF.md:18). 채용 요구·팬 글·외부 재현만으로 “D4가 쓴 도구”를 확정할 수 없다(02_hud_ui.md:112,161–164,254–256).
2. **R1/R3/R4 기하:** D132·바닥여백4~8이면 중심은 바닥 위70~74px. 판72~76 위로 반지름20~30%=13.2~19.8만큼 중심을 올리면 중심85.2~95.8, 꼭대기151.2~161.8로140을 넘는다. y 아래 방향의 덧셈으로 읽으면 “구체 중심이 판 윗선보다 위”와 반대다. §1에서는 틀 잘림29.6을 허용하고 액체여백4~8로 대상을 바꾸기도 한다(02_hud_ui.md:26,28–29,57,78–89).
3. **R2 산식:** 132+18+671+18+132=971의 중심간격은839, 중심x540.5/1379.5다. 같은 연구의 약800/560·1360은 다른 배치다. 목표를 하나로 확정해야 한다. :89의 첫 목업1x 판정 후±10% 조정도 허용 범위일 뿐, 실물 판정을 대체하지 않는다(02_hud_ui.md:27,83,89,98).

## 7. Mac 캡처가 오면 갱신할 항목

같은 커밋·캐릭터·장착·자원 상태·카메라에서 현재/--hud-proto=a/--hud-proto=b를 비교한다. C는 문서뿐이므로 캡처 인자가 없다. H1_unity_prototype.md:159–180의 인계를 따르되 하니스 기존 기하 PASS를 A/B 화면 합격으로 바꾸지 않는다.

1. **R8 글자:** 1920×1080 전체·하단1x/3x에서13키·쿨다운·현재/최대값의 ink 높이/폭/획/대비. 빈 키·SHFT/CTRL/SPC·9×11 마우스 그림·720p7px 라벨을 우선 확인. 실제 읽기와 입력 확인을 분리한다.
2. **R1·R3 접지/가림:** 같은 시작·전투공터·보스입구에서 접촉선을 재고 숲·밝은/어두운 바닥·HUD 근처 적/탄막을 비교. 가시·그림자 포함 경계, 가까운/먼 적의 가독성을 갱신한다.

4. **U1↔H1 box model:** 브라우저 computed style/DOM rect로 소켓 border-box/padding box/아이콘/cd를 각각 재고 Unity와 대조.34/38/46 대36/40/48, clip-path/그림자 및 실제 PNG 잉크를 분리한다.
