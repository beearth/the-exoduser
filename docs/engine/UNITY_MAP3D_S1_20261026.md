## 좌표 매핑 결정

- Godot: 1유닛=1px, 지면 XZ, `X=px_x`, `Z=px_y`(남쪽=+Z), 카메라는 +Z 쪽에서 -Z를 본다(우수계).
- Unity는 좌수계라서 Z만 반사한다: **Unity 위치 = (px_x, 높이, −px_y)**. 모든 위치·방향에 같은 반사를 적용하면 좌수계 카메라가 Godot 화면을 그대로(북쪽=위, 동쪽=오른쪽, 좌우반전 없음) 만든다. 근거: 반사한 장면 + 반대 손잡이 카메라 = 같은 이미지. 시뮬레이션 좌표(2D px, +Y 아래)와 수치는 변경 0이고, 기존 2D 경로의 100px/unit·Y반전 매핑과 섞지 않는다.
- 빌보드는 카메라 forward를 지면에 투영한 방향으로 Y축 고정(yaw 0이면 카메라 정면 평면).

## 맥북 총괄 검수 (2026-10-26)

- **인수 범위**: 카메라·원근·지면 클램프·지면 청크·빌보드 스프라이트·key/fill/ambient. mass 없는 비교(`unity_pc_win_refs/map3d_s1_nomass.jpg`)에서 Godot D와 지면 질감·나무·플레이어 위치/크기·가시 영역이 사실상 겹친다(밝기 차는 Godot D에 2단계 fog·glow·grade가 이미 들어간 탓).
- **판정 보류: authored mass 외관**. mass 포함 화면(`map3d_s1_mass.jpg`)에서 가장자리 벽 mass(높이 80, `bound_w.png`)가 지면보다 밝고 끊겨 보여 게임 톤에 맞지 않는다. 그러나 Godot 기준 캡처도 51개 중 3개만 mass가 생성된 상태(`_sync_visible_masses` 캐시 선점 추정, native_perspective_view.gd:521-531)라 원본 대비 판정을 할 수 없다 → **mass가 정상 생성된 Godot D 기준 캡처를 다시 찍은 뒤** 외관 판정·2단계 조명 보정. 그때까지 mass는 코드만 유지.
- 종료 코드 0xC0000005는 `UNITY_PC_EXIT_CRASH_20261026.md`의 6000.4.8f1 엔진 결함(오프셋 0x107a81)과 같은 계열로 보며 이 단위 문제로 다루지 않는다.
- NativeGame patch(`MAP3D_S1_nativegame.patch`)는 적용 상태 컴파일 미검증 — 2단계 때 적용 빌드로 확인.
