## 저프레임 구분

- 헤드리스(창·GPU 없음)에서도 같은 구간이 7~9fps였다 → 창 겹침만의 문제가 아니라 실제 CPU 과부하. 같은 조건 P코어(논리 0~15) 고정 측정에서도 수정 전 8~12초 구간 12~27fps.
- 프로파일(물리 틱 단위, 노드 구간 표식): 플레이어 물리 10.4ms/틱 중 `stats_changed.emit()`→HUD `_refresh` 4.5ms(스태미나가 바뀌는 틱마다 HUD 전체 재계산), E 제어 원천 중복 계산 약 1.6ms. 물리 한 틱이 16.6ms를 넘자 Godot가 프레임마다 물리를 최대 8틱 몰아 돌려 7~9fps로 무너졌다(물리 56~60/s 유지, 그리기 7/s).
- 수정(원본 동작 불변):
  - `hud.gd` — `stats_changed`는 표시 갱신 예약만 하고 실제 갱신은 다음 `_process` 1회(그리기 직전 값, 기존 30Hz 갱신 유지).
  - `native_combat_qe_adapter.gd` — `advance_e_control`이 바로 앞 `is_native_e_control_ready()`가 같은 틱에 읽은 원천을 재사용(그 사이 쓰기 없음).
  - 레슨 뒤 iframes 복원(위 표)으로 레슨 직후 링 적 접촉이 원본처럼 늦춰져 피격 처리 부하도 원본 시점으로 이동.
- 결과(같은 시나리오, P코어 고정 헤드리스): 수정 전 1초 90 → 8초 20 → 11초 13fps / 수정 후 0~12초 96~144fps. 창 모드(고정 없음, 사용자 플레이 창 동시 실행)는 수정 후 대체로 30~60fps, 순간 8~19fps 구간 남음 — 창 모드 순간 저하는 E코어 배치·사용자 창(Godot 1개) 동시 실행과 분리 측정하지 못했다(미확인).
