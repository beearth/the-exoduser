## 1. 목표 장면·레퍼런스 (무엇을, 왜)
- 목표 장면: 1-1 원근 카메라(피치 34° 고정)에서 캐릭터 키 = 화면 높이 약 5.6%인 1x 화면. 이 크기에서 동작이 읽혀야 한다.
- 레퍼런스: 디아블로4(가독성, 층 애니메이션·히트 방향), Phantom Blade Zero(끊기지 않는 흐름·캔슬), 데드셀·길티기어 Xrd(3D를 저해상도 2D처럼 읽히게 하는 방식).
- 왜: 사용자 평가 "동작 하나하나가 다 쓰레기"(11-05). 원인은 사이 프레임 보간이 저해상도 렌더에서 뭉개지고, 예비·접점이 안 읽히는 것이다.

## 2. 디렉션 원칙
1. 키포즈 3~5장이 1x에서 읽힌 뒤에만 사이 프레임을 만든다. 이유: 읽히지 않는 동작은 프레임을 늘려도 안 읽힌다.
2. 예비 정점·접점은 실제 인체 한계보다 과장한다. 이유: 저해상도에서 작은 변화는 텍셀에 묻힌다.
3. 예비 정점과 접점은 포즈를 몇 틱 홀드한다. 이유: 2D 느낌과 가독성을 함께 얻는다.
4. 모션이 판정을 붙잡지 않는다. Core가 캔슬을 허용한 틱에 클립을 버리고 새 동작으로 섞는다. 이유: PBZ식 흐름, 입력 반응.
5. 발은 미끄러지지 않는다. 보폭은 시간이 아니라 이동 거리로 진행한다. 이유: 미끄러짐이 가장 싸구려로 보인다.
6. 피격은 방향이 있는 덧셈(additive) 반응이다. 하체는 고정한다. 이유: 경직 길이는 Core가 정하므로 표현은 층으로 올린다.
7. 시뮬레이션 시간은 멈추지 않는다(R3). 접점 강조는 대상 한 개의 포즈 홀드와 섬광으로 한다. 이유: 적이 많은 화면에서 전역 정지는 끊김이다.
8. 같은 영웅의 모든 동작은 DESIGN LOCK 실루엣(머리·장신구·무기)을 유지한다. 이유: 캐릭터 통일(CLAUDE.md 4.2-6).
9. 모든 키포즈는 단색 실루엣 1x 캡처로 먼저 검수한다. 이유: 재질이 실루엣 결함을 가린다.
10. 점 금지: 호흡 등 미세 흔들림이 3x 크롭에서 잔점으로 보이면 진폭을 0으로 한다.
11. 키포즈는 근·중·원거리 세 깊이에서 모두 단색 실루엣으로 읽혀야 한다. 이유: 원근 카메라(LOCK)에서는 같은 동작도 깊이가 두 배면 픽셀 높이가 절반이라, 근거리 통과가 원거리 통과를 보장하지 않는다 [추정·계산, codex_3d_pixel §2·§4.1].
12. 블렌드·리샘플·압축이 극점·접점 포즈를 지우지 않는지 임포트 뒤 같은 시각으로 비교한다. 이유: 전환 블렌드가 중간 포즈를 다시 만들어 키 대비를 없앨 수 있다 [사실 ProPixelizer 문서 / 추정 적용, codex_3d_pixel §4.3·4.4].
13. 포즈 개수를 줄이는 일과 동작 시간을 줄이는 일은 별개다. 판정 시간은 Core 그대로 두고 포즈 노출만 재배분한다. 이유: 그림을 많이 넣는다고 타격감이 좋아지지 않는다(Skullgirls 21→15장, 45→29장 정리 사례) [사실 GDC / 추정 적용, codex_motion_direction].
14. 모션의 접점 포즈·VFX·Core 판정 시점은 한 이벤트 시각으로 맞춘다. 이유: Hades는 Nova의 폭발 속도와 VFX를 맞추는 수정을 공식 기록했다(정확한 지연값 미확인) [사실, codex_motion_direction].
15. 카메라를 향한 전후 베기는 투영 폭이 작아진다. 옆 방향에서만 읽히는 포즈는 통과시키지 않는다. 이유: 원근 투영 [추정, codex_3d_pixel §4.1].

| 역할 | Unity 추천 | UE5 대응 |
|---|---|---|
| 모델/리그 | Blender 수동 리그(Humanoid 24본 이름 규칙) | Blender 수동 리그(UE 마네킹 호환 본 이름 또는 커스텀 스켈레톤) |
| 키 애니메이션 | Blender 손키(본 작업), Mixamo는 걷기·달리기 원형만 | 동일 |
| 상태 연결 | Animator + 지금 전사 HumanPose·수동 IK 유지 | Animation Blueprint 상태머신 |
| 발 고정 IK | 영웅은 기존 수동 IK 유지 | Control Rig 발 IK |
| 픽셀 렌더 | **액터별 직교 캡처를 PixelActorPass 1개(아틀라스 RT, Point)로 묶기** — TOOLCHAIN a-1 [제안], 승인 전에는 현행 리그 픽셀 RT(UNITY_RIG_PIXEL 계약) 유지 | SceneCapture2D → 저해상도 Render Target(기본 픽셀화 기능 없음, HDR→LDR 후처리 깨짐·TSR 잔상 보고 [단일]) |
| 검수 | 1x 실루엣 캡처 + 10초 무음 영상 | 동일 |

- 대안: Cascadeur(리타깃이 Pro 판, 반입 끊김 보고 [단일]) / 생성형 모션(홀드·과장 제어 불가 [추정]). 둘 다 이번엔 제외.
- TOOLCHAIN §2-6과 대조(2차): 동작 = Blender 손키(Mixamo는 원형 참고만), 런타임 = 영웅은 HumanPose·수동 IK 유지·신규는 Animator + Animation Rigging, 리깅 = Blender 수동(Rigify, Humanoid 24본). 이 문서의 추천과 같다. 차이는 픽셀 렌더 한 줄(위)뿐이고 D04-5로 올렸다. 원근 카메라 전체를 저해상도 RT 한 장에 그리는 안은 pixel creep(직교에서만 해결 [사실·출처 2])으로 제외한다.
- 커스텀 툴 1개 명세 — "타이밍 표 검증기": 입력 = §3.1 타이밍 표(CSV) + Core 상태 길이 JSON, 처리 = 표의 총 틱이 Core와 일치하는지 대조, 출력 = 불일치 목록. 사용자 = 구현 레인. 만드는 사람 = 구현 Sonnet 레인(Core 읽기 전용). 이유: 표와 Core 불일치가 가장 흔한 사고다.

## 5. 절차
### 5.1 공통 (입력 → 작업 → 출력 형식)
1. 입력: DESIGN LOCK 시트, §3.1 타이밍 표(Core에서 총 틱 읽어 채움). 표 없으면 키 작업 금지.
2. 작업: 회색 박스 모델로 키포즈 3~5장 → 1x 단색 실루엣 판정 → 홀드·과장 적용 → 사이 프레임 → 곡선 정리. 30fps 이상 키.
3. 출력: FBX, 클립명 `<영웅>_<동작>_<번호>`(예: `warrior_atk_1`), 루트 이동 키 없음(제자리), 60fps 표본, 클립 길이 = Core 상태 길이 ÷ 60초.
4. 같은 동작 A/B: 보간 그대로 / 홀드 / 전체 12fps 계단 / 포즈 시각 양자화(§3.3, Fpose는 12·15·20 후보) 4안 10초 영상 비교 후 확정(연구 남은 일 2). 양자화안은 판정·이동 시간을 건드리지 않고 이벤트(접점) 누락·중복이 없는지도 검사한다.
5. 임포트 뒤 비교: 원본 핵심 포즈(예비 정점·접점·회복 정점)의 시각을 기록하고, 임포트·블렌드 적용 뒤 같은 시각·앞뒤 시각 캡처를 겹쳐 극점이 약해졌는지 본다(원칙 12). 문제가 생긴 클립만 블렌드 길이·리샘플·압축 오차를 조정한다.
6. 수정 비용 기록: 새 클립 첫 제작 시간과 기존 클립 타이밍 재수정 시간을 따로 적는다(Dead Cells는 원화 양이 아니라 재수정 비용을 줄이는 쪽으로 파이프라인을 짰다 [사실], codex_3d_pixel_small_team §3·§9).
7. 첫 범위: 키샷 단계(TOOLCHAIN S4)는 영웅 1명 × 대기·걷기·1~3타·스킬 1·피격·구르기만. 전부 1x 판정 PASS 뒤에 다음 영웅·스킬로 넓힌다(소규모 팀 사례: 줄일 범위를 화면 밖에서도 찾는다).
### 5.2 Unity 반입
- Import: 인간형 Humanoid, 비인간 Generic. 루트 모션은 Bake Into Pose(Y, XZ, 회전 모두). 압축 회전 오차 0.1°.
- Animator 상태 = Core 상태 1:1. 재생 속도 = 클립 길이 / Core 상태 길이. 블렌드 0.12~0.20초, 캔슬 0.06~0.10초.
- 접지 위상에서만 IK 가중 1. 렌더는 픽셀 RT 레이어(30), 정수배 스케일, 발밑 텍셀 스냅. D04-5 승인 뒤에는 PixelActorPass 아틀라스로 이전한다(액터별 직교 뷰포트, Point 확대, 합성 순서 첫 비교안: 불투명 → 외곽선 → 투명/VFX → 확대 → UI [추정], 확정 사양 아님).
- 임포트 검사(원칙 12): Resample Curves·압축 오차는 클립별로 Off와 비교한 뒤에만 켠다. 출시 기본값으로 단정하지 않는다. 카메라·클립 비교는 한 변수씩(루트 스냅, 기준 깊이 스냅, stepped pose) 하나씩 한다. 원근 카메라를 직교로 바꾸지 않는다.
### 5.3 UE5 반입 (대응만)
- Import: 스켈레톤 재사용, Root Motion 끔. Anim Montage로 공격, Anim Notify로 접점·홀드 이벤트. Animation Blueprint 전환 시간 = 블렌드 값. 발 IK는 Control Rig. 픽셀 렌더는 기본 기능이 없어 SceneCapture2D 직교 투영 → 저해상도 Render Target 우회(포럼 보고뿐, 품질·비용 미검증 [단일]).

## 6. 합격 기준
- 키포즈 단계: 1x 단색 실루엣으로 동작이 읽힌다(공격 1·2·3타 실루엣 서로 구분).
- 비교판: 우리 1x 클립을 같은 크기로 D4·PBZ 공개 영상 옆에 놓는다(감각 대조, 복제 아님). 1920×1080과 3840×1080 모두 성립.
- 10초 무음 영상: 끊김 0, 발 이동 ≤1텍셀, 예비→발동→회복이 읽힘. 3x 크롭 점 0.
- 타이밍: 표와 Core 상태 길이 일치. 예산: 영웅 1명당 클립 수는 §3.1 행 수 + 콤보·스킬 수.
- 깊이 판정(2차): 1x 실루엣 판정을 근·중·원거리 세 곳에서 한다. 가장 먼 깊이에서 예비 정점과 접점이 구분되지 않으면 FAIL(먼 적을 지우는 것과 같다). 정지 포즈뿐 아니라 정상 속도 재생에서도 확인한다. 원본 저해상도와 정수 확대 최종 화면 둘 다에서 본다.
- 임포트 판정: 블렌드·압축으로 극점·접점이 사라지면 FAIL. 시각과 Core 접점 시각 불일치도 FAIL.
- 정지 뒤 확인: 접지 발 ≤1텍셀, 무기 끝과 소켓 정렬, 루트 스냅·홀드·보간이 서로 다른 시각에 적용되지 않는다.

## 7. 금지
- Core 상태 길이·무적·캔슬 틱을 표현 때문에 바꾸지 않는다.
- 히트스톱으로 시뮬레이션 정지(D07-1 결정 전).
- 루트 모션으로 좌표 이동. 카메라 피치 변경.
- PixelLab으로 캐릭터 새로 생성(CLAUDE.md 4.2-6). 레퍼런스 에셋 반입.
- 모캡 그대로 사용(과장 없음). 점묘·디더링 잔상.
- 공개 위키·측정 수치를 Core 상태 길이·무적·패링 창 변경의 근거로 쓴다. 평균값 합성, 출처 충돌 수치(Elden Ring 구르기)를 목표값으로 고정.
- 근거 없는 최소 픽셀 수·fps 확정(연구가 미확인으로 남긴 값). 원근 카메라를 직교로 치환하거나 전체 화면을 저해상도 RT 한 장에 그리는 방식.
- 방어 성공 창을 무적으로, 어느 한 게임의 무적을 다른 상태에 대입.
