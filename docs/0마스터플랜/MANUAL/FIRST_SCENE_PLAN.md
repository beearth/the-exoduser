## 5. 작업 순서·예상 시간·합격 및 중단 기준

### 공통 판정 절차

- 매 단계 PC의 소스/설정 확인 뒤 **Mac 실제 렌더 캡처 → Mac 담당과 총괄의 눈 판정**을 받아 다음 단계로 간다. 캡처가 없으면 `PENDING`, 화면 결함이면 `FAIL`이다. 컴파일·정적 수식·투과율·파일 존재를 시각 `PASS`로 바꾸지 않는다.
- 모든 단계에서 HUD 없는 전체 프레임 **1920×1080·3840×1080**과 같은 지점의 **1x·3x 크롭**을 본다. 3x는 결함 확대 검사이며 최종 화면을 재구도하는 수단이 아니다. 초기 단계도 실제 Unity 카메라 렌더가 필요하고, 마지막은 반드시 실제 적·전투·이동을 포함한다.
- 같은 소스/씬 상태의 Mac 검증 빌드는 **1회**로 한다. 프리셋 전환만으로 비교할 수 있으면 재빌드하지 않는다. 다음 단계에서 소스·씬이 바뀐 경우 필요한 새 상태를 한 번 빌드한다. 실패는 원인 변경 없이 반복 실행하지 않는다.
- 결과는 `단계 / 소스 SHA / 씬 / 장치·API·해상도·렌더 스케일·AA / 카메라 / 캡처·핵심 로그 / PASS·FAIL·PENDING / 가장 큰 차이`로 남긴다. 초기 거친 실물 PASS를 최종 키샷 PASS로 확대하지 않는다.

### MoodLab 사고 재발 방지

[사실·사용자 지적] MoodLab은 정적 검사만으로 격리 실패와 프리셋 차이 부족을 놓쳤다. 인계 문서의 ‘추가 효과 없음’·‘본선 초기화 없음’ 설명은 실행으로 확인할 주장이다. 구문·GUID·시야/투과율 계산 PASS는 런타임 격리나 시각 차이 증명이 아니다.

1. **격리를 먼저 본다.** 연구 진입에서 본선 카메라·HUD·오디오·저장 초기화가 먼저 생기는지 로그와 캡처를 함께 본다. 같은 단계의 전역 초기화 훅 순서를 믿거나, 본선 로드 뒤 루트만 끄고 성공 처리하지 않는다. 정상 실행의 전후 화면도 대조한다.
2. **한 효과씩 본다.** `기준 → 거리 안개 → 기준`, `기준 → 높이 안개 → 기준`, `기준 → LUT → 기준`처럼 비교한다. 유지할 다중 프리셋이 있다면 `a→b→c→d→a` 복귀도 본다. 이름·RGB 숫자만 다르고 실제 화면 차이가 작으면 후보를 통합/폐기한다.
3. **차이와 가독성을 함께 본다.** 1x에서 늪 저층·고목/북쪽 배경 중 어느 영역이 어떻게 달라졌는지 총괄이 설명할 수 있어야 한다. 동시에 먼 적이 보이고 3x 점 0이어야 한다. 의도한 차이가 없으면 강도를 무작정 올리지 않고 구현/합성 경로를 조사한다.
4. **표식에서 실제 적으로 넘어간다.** 초기 대역의 시야 통과는 지형·광원 초벌 관문만 통과한다. 최종 화면은 같은 소스의 Mac Player에서 실제 적과 전투·시간 변화가 있어야 한다.

## 7. 성능·호환성·최종 인수 조건

[사실·공식 기능 경계] Unity 6000.6 기능표는 URP의 거리 안개와 HDRP의 Local Volumetrics를 구분한다. URP에 HDRP Fog/Water 기능이 그대로 있다고 가정하지 않는다. 출처: [Unity 공식 렌더 파이프라인 기능 비교](https://docs.unity.com/en-us/engine/6000.6/manual/render-pipelines/choose-a-render-pipeline/feature-comparison).

[추정·측정안] `our_tech_audit.md`의 정적 위험을 다음 관문으로만 사용한다. Core의 배열/AI 루프 최적화, 전역 Resources 정리·Addressables 전환, 공통 임포터 수정은 이번 장면 작업에 끼워 넣지 않는다.

- 고목/소품 가시 인스턴스·tri·draw/SetPass·그림자 패스, 물 반사·수면 패스, 리그 적 RT 요청 수와 시간, 후처리·안개 비용을 같은 카메라·적 수·해상도에서 Mac 담당이 확인한다. 보유 메시를 군집화했다고 성능이 자동 개선됐다고 쓰지 않는다.
- CPU/GPU 프레임 시간과 GC, 텍스처/RT 실제 상주 메모리, 진입/첫 가시 프레임 지연을 기록한다. Git 원본 byte·PNG 크기·정적 tri 합계로 FPS나 VRAM을 확정하지 않는다. 플랫폼에서 GPU 지표를 얻지 못하면 0ms 대신 미측정으로 적는다.
- 목표 FPS/프레임 ms·메모리 한도는 **매뉴얼 확정 때 총괄이 지정할 값으로 현재 미확인**이다. 승인된 예산과 동일 장치 기준 캡처가 없으면 성능 PASS를 주지 않는다. 예산 초과 시 새 광선/반사/후처리부터 한 요소씩 줄여 원인을 좁히고, 먼 적·34° LOCK·점 0을 희생하지 않는다.
- 파일·출처·라이선스·Unity/URP/Metal 컴파일·필수 Resources·리그 RT 합성 중 하나라도 미확인이라면 그 관문은 `PENDING`이다. 유료 생성 2회 같은 조형 결함, 시각 개선 없는 프리셋 반복, 격리/세이브 침범은 중단하고 총괄에게 재계획을 올린다.

### 최종 전달과 산출물 관리

최종 인수는 **같은 소스 SHA의 Mac 빌드**에서 다음 항목을 모두 확인해야 한다.

1. 카메라 34° LOCK과 기존 원근·표시 크기 유지, 양쪽 늪·전경 고목·목교·가까운 교전·북쪽 움직이는 적 동시 식별.
2. HUD/디버그 표시 없는 필수 두 해상도 원본과 21:9 확인, 1x 비교·3x 결함 검사, **10초 무음 실제 플레이 영상**, 출처를 식별한 레퍼런스와 같은 표시 크기의 비교판. 레퍼런스의 대형 자산을 프로젝트에 반입하지 않는다.
3. 접지·셰이더/수면·전환 잔류·점/그레인·가림·카메라/시간 변화 검사 통과, 새 씬 격리와 정상 경로 보존, Core diff 0, 승인 성능 예산 충족.
4. 총괄의 직접 화면 판정. 정적 검사/PC 컴파일/환경 대역 캡처만 있으면 최종 완료가 아니다. 사용자 거절은 FAIL로 처리한다.

[추정·운용] 빌드·캡처·로그는 담당이 정한 **고정 폴더에 최신 검토 세트 1개**만 둔다. 단계별 폴더·시도별 빌드·before 사본을 쌓지 않는다. 필요한 기준/결과는 최신 비교판 한 세트로 합쳐 검토하고 이전 세트는 정리한다. 확인이 끝난 시도 빌드·캡처는 보관하지 않고 보고에 소스 SHA·판정·핵심 로그 요약을 남긴다. 사용자가 여는 승인된 실행본/정식 전달물은 일반 운영 매뉴얼의 예외를 따른다. 작업 산출물이 20GB를 넘으면 다음 생성·빌드 전에 정리하며, 타인 WIP·세이브·배포물은 건드리지 않는다.

**이번 작성의 완료 범위:** 계획 문서 1개. 자산 구매/생성·코드/씬 제작·Unity 실행·빌드·Mac 캡처·실게임/품질 판정·커밋·push는 수행하지 않았으며 모두 후속 관문이다.
