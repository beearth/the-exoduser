# 리깅 3D의 실시간 픽셀 렌더와 읽히는 애니메이션 연구

작성·웹 열람: 2026-11-05. 대상: **Unity 6000.6.7f1 / URP / 원근 카메라**. 산출물은 이 연구 문서뿐이다. 구현·Unity 실행·이미지/영상/모델/게임 파일 다운로드·에셋 반입·로그인·구매는 수행하지 않았다. 커밋·push는 총괄 검토 뒤의 별도 작업이다.

## 1. 근거를 읽는 방법과 결론

- **[사실]**은 원문에서 확인한 설명이다. 저자의 사례·제품 문서·논문의 결과는 각각 그 환경에 한정한다. **[추정]**은 그 근거에서 유도한 수학적 계산, Unity 이식 설계 또는 검증 전 가설이다. `[추정·계산]`의 숫자는 명시한 가정의 산술 결과이지 실측값이 아니다. 확인하지 못한 설정·성능·적정치는 **미확인**으로 쓴다. 아래 `[U1]` 같은 표기는 마지막 출처 목록의 URL로 연결된다.
- **[사실]** 6000.6.7f1의 공식 릴리스 페이지와 Unity 6000.6의 Render Graph 문서를 확인했다. 이 프로젝트에 설치된 URP 패키지의 정확한 버전, Renderer 설정, 그래픽 API는 미확인이다. 에디터 버전만으로 패키지 패치 버전이나 예제 호환성을 확정하지 않는다. [U1] [U2]
- **[추정]** 우선 검토할 조합은 **원근 유지 → 고정 저해상도 타깃 → 깊이/노멀 또는 ID 외곽선 → 정수 확대 → 게임 카메라에서 설계한 키 포즈**다. 카메라 스냅은 별도 실험으로 둔다. 근거는 픽셀 확대·외곽선·포즈 설계가 서로 다른 문제를 해결하며, 원근에서는 하나의 카메라 격자가 모든 깊이의 움직임을 고정하지 못한다는 점이다. [U4] [O1] [O3] [P1] [A1]
- **[사실]** Dead Cells 원저자의 설명은 3D 골격 애니메이션을 저해상도 PNG 프레임과 노멀맵으로 출력하는 제작 파이프라인이다. 이를 게임 중 리깅 메시를 매 프레임 렌더한 사례로 인용할 근거는 없다. 실시간 작업에 가져올 핵심은 포즈·타이밍·빠른 수정 방식이다. [D1]

## 2. 원근 카메라에서 먼저 분리할 문제

**[사실]** 저해상도 3D의 pixel creep는 이동할 때 표면을 구성하는 픽셀이 달라지는 현상이다. 카메라 이동뿐 아니라 물체의 상대 이동에서도 발생하고 외곽선에서 특히 눈에 띈다. 비정수 확대는 별도로 픽셀 행·열의 폭 불균일과 디더 무늬의 간섭을 만들 수 있다. [P4]

**[사실]** Unity는 원근 시야의 거리 `z`에서 높이를 `2 × z × tan(FOVy/2)`로 계산한다. ProPixelizer의 직교 스냅 도구도 원근의 크기 변화는 해결 범위 밖이라고 명시한다. [U3] [P1]

**[추정·계산]** 대칭 원근 투영, 고정 FOV, 저해상도 타깃 높이 `H`, 카메라 전방축으로 잰 양의 깊이 `z`를 가정하면 다음과 같다. 지면 거리나 카메라와의 유클리드 거리를 `z`에 대신 넣으면 안 된다. `h`는 카메라 평면과 평행하고 같은 깊이에 놓인 구간의 길이다. 기울어진 캐릭터 전체 높이는 실제 투영으로 확인해야 한다. [U3]

```text
f = H / (2 × tan(FOVy/2))       // 저해상도 픽셀 단위 초점거리
q(z) = z / f                  // 해당 깊이에서 저해상도 1픽셀에 해당하는 월드 길이
h_px = f × h / z              // 같은 깊이의 평행 구간이 차지하는 픽셀 수
|Δp(z)| = f × |ΔcameraXY| / z  // 회전 없는 카메라 평행 이동의 화면 이동량
```

**[추정·계산]** 따라서 같은 크기의 평행 구간은 깊이가 두 배가 되면 픽셀 높이가 절반이다. 기준 깊이 `z0`를 한 픽셀만큼 움직이게 하는 카메라 이동은 `2z0`에서 반 픽셀 이동을 만든다. 기준 면을 정렬해도 다른 깊이는 다시 래스터화된다. 실제 FOV·근/중/원거리 캐릭터 높이·최소 무기 두께는 **미확인**이다. 먼저 그 값을 측정해야 해상도를 결정할 수 있다. [U3]

## 3. 기법별 구현 연구

### 3.1 고정 저해상도 RenderTexture와 정수 확대

**[사실]** Unity의 URP Pixel Perfect 문서는 임시 저해상도 텍스처 확대, Point 필터, 비율 보존용 여백을 설명한다. Point는 선명함을 유지하지만 shimmer가 생길 수 있고, Retro AA는 bilinear 기반으로 shimmer를 줄이는 대신 경계가 부드러워질 수 있다. 이 문서는 2D 스프라이트용이며, 별도 2D Pixel Perfect 패키지는 Built-in용이라고 명시한다. [U4]

**[추정] 구현 절차 —** ① 원근 카메라의 게임 장면을 고정 `W×H` 타깃으로 직접 렌더한다. ② 색상·깊이·노멀·ID를 같은 카메라 행렬과 타깃 격자로 맞춘다. ③ 저해상도에서 외곽선을 처리한다. ④ Point 샘플로 출력하고 UI는 목적에 따라 나중에 합성한다. 고해상도 이미지를 마지막에 축소하는 것과 실제 저해상도 래스터화는 비용·가시성에서 같다고 가정하지 않는다. [U2] [U4] [O1]

**[추정·계산] 수치 —** 출력 `1920×1080`을 가정하면 `320×180`은 6배, `480×270`은 4배, `640×360`은 3배 정수 확대다. 이는 비교용 산술 예시이며 채택 해상도가 아니다. 비율이 다르면 `s = floor(min(출력폭/W, 출력높이/H))`로 정수 배율과 여백을 계산한다. `s<1`이면 원본보다 작은 출력이므로 별도 축소 정책이 필요하다. [U4] [P4]

**[추정·계산] 비용 —** `320×180`은 57,600픽셀로 1080p 픽셀 수의 `1/36`, `640×360`은 `1/9`이다. 이는 타깃 면적 비율일 뿐 프레임 시간 개선 배수가 아니다. 스키닝·그림자·CPU 제출·최종 확대는 따로 남으며, 추가 패스와 복사도 비용을 쓴다. GPU ms와 제작 공수는 미확인이다. [U2] [U7]

**[사실] 실패 사례 —** ProPixelizer 저자는 저해상도 타깃의 비정수 확대가 픽셀 폭 불균일과 디더의 모아레를 유발한다고 설명한다. [P4]

**[추정] 원근 적용 한계 —** 이 방식은 화면의 픽셀 격자를 고정하지만 물체 표면의 픽셀 구성을 고정하지 않는다. 전후 이동·회전·관절 변형의 creep는 남는다. 2D Pixel Perfect 컴포넌트를 원근 3D 해결책으로 그대로 채택할 근거는 없다. [U4] [P1]

### 3.2 t3ssel8r류 깊이·노멀 외곽선과 볼록 모서리 강조

**[사실] 출처 범위 —** David Holland는 자신의 Godot 재현에서 깊이·노멀 텍스처, 상하좌우 이웃, 한 픽셀 선, 볼록 모서리 판별 휴리스틱을 사용했다고 설명한다. 이는 **재현 저자의 구현**이다. t3ssel8r의 원본 Imgur는 본문이 JS 의존 안내로만 열렸고 원본 YouTube의 상세 본문은 확보하지 못했다. 원저자의 정확한 커널·임계값·URP 지원은 미확인이다. [O1] [R1] [R2]

**[추정] 구현 절차 —** ① 현재 색상과 선형화한 깊이, 디코딩한 노멀을 읽는다. ② 저해상도 기준 `(1/W, 1/H)` 간격의 상하좌우와 비교한다. ③ 깊이 불연속으로 실루엣 후보를, 노멀 차이로 접힘 후보를 만든다. ④ 깊이의 앞/뒤 관계와 방향을 이용해 어느 쪽 픽셀에 선을 소유시킬지 정한다. ⑤ 볼록/오목 판별을 별도로 검증하고 내부 강조선과 실루엣 색을 분리한다. `1-dot(n0,n1)`만으로 볼록·오목을 확정하지 않는다. [O1] [O2] [O3]

**[사실] 수치와 함정 —** Roystan의 Unity 2018.3 튜토리얼에는 노멀 임계값 `0.4`와 서로 다른 깊이 임계값 예시가 있다. 깊이 값이 비선형이라 일정 임계값만 쓰면 원거리 선이 빠지고, 카메라를 비스듬히 보는 면에는 가짜 선이 생긴다고 설명한다. 이 숫자는 해당 연산·버퍼에 속하며 6000.6의 권장값이 아니다. 대상 적정 임계값은 미확인이다. [O2]

**[추정·계산] 비용 —** 중심과 상하좌우 5위치를 깊이·노멀 각각 읽고 색상 중심을 한 번 읽는 단순 구성은 논리상 `5+5+1=11`회 텍스처 읽기다. 캐시·컴파일 최적화·깊이 복사·노멀 생성 패스는 포함하지 않은 연산 개수이며 GPU ms는 미확인이다. 노멀 요청으로 생기는 실제 패스는 Render Graph에서 확인해야 한다. [O1] [U7]

**[사실] 실패 사례 —** Holland는 모든 모델·각도에 완벽한 외곽선을 얻는 데 의문을 표하고 장면별 조정을 요구한다. KYRIOTA는 깊이 차이를 양방향으로 쓰면 선이 두꺼워지고, 노멀 차이만 쓰면 오목 모서리나 떨어진 물체 사이에 원치 않는 선이 생기는 문제를 기록했다. [O1] [O3]

**[추정] 원근 적용 한계 —** 원근에서도 화면 공간 검출은 가능하지만, 깊이·면의 경사에 따른 임계값 보정이 필요하다. 고해상도 깊이와 저해상도 색상을 서로 다른 UV로 읽으면 실루엣이 어긋날 수 있다. Unity의 깊이 복원 절차처럼 reversed-Z·NDC 범위·역투영 행렬을 맞추고, 노멀은 같은 공간으로 통일해야 한다. 오래된 예제의 버퍼 이름·인코딩·호출 코드를 그대로 복사하지 않는다. [U5] [O2] [O3]

### 3.3 ID 기반 실루엣과 선택적 내부 선

**[사실]** ProPixelizer는 같은 ID와 정렬된 픽셀 격자를 가진 여러 메시를 하나의 실루엣으로 취급하고, 겹치는 물체에는 깊이 검사를 수행한다. 내부 모서리는 노멀 및 선택적인 깊이 검사로 다룬다. [P2]

**[추정] 구현 절차 —** ① 저해상도 별도 버퍼에 캐릭터 단위 ID를 기록한다. ② 몸·갑옷·장비 중 하나로 보일 부분은 같은 ID를 쓴다. ③ 이웃 ID가 다를 때 경계 후보를 만들고 깊이로 전경의 선만 남긴다. ④ 손·무기 구분처럼 필요한 내부 선은 별도 마스크 또는 노멀 검사로 추가한다. ID 버퍼에는 보간·블러가 섞이지 않게 한다. [P2] [U2]

**[추정·계산] 수치·비용 —** 예를 들어 R8 정수 ID를 쓴다면 비트 수상 256개 코드이며 배경 1개를 예약하면 255개가 남는다. 이는 저장 형식 가정일 뿐 제품 사양이 아니다. 형식 지원·렌더 타깃 개수·ID 재사용 정책은 미확인이다. 추가 기록 패스나 attachment, 이웃 읽기, 같은 ID의 부속품 관리가 필요하고 ms·인일은 미확인이다. [P2] [U2]

**[추정] 실패 사례와 원근 한계 —** 서로 다른 캐릭터가 같은 ID를 공유하면 접촉 경계를 잃을 수 있고, 몸·무기를 다른 ID로 두면 불필요한 분리선이 생길 수 있다. ID만으로 같은 물체 내부의 접힘은 구별하지 못한다. 깊이 검사 없이 배경 물체 선을 합성하면 가림이 틀어진다. 원근에서도 적용 가능하나 멀리서 한 픽셀보다 얇아져 기록되지 않은 물체를 복구하지는 못한다. [P2] [U3]

### 3.4 직교 카메라 스냅과 화면 오차 보정

**[사실]** Holland가 설명한 방식은 카메라를 뷰 정렬 texel 격자로 스냅한 뒤, 렌더 결과를 스냅 오차만큼 화면에서 되돌리는 두 단계다. ProPixelizer의 스냅 도구는 직교 투영을 대상으로 하며 렌더 전 위치를 스냅하고 이후 복원한다. [O1] [P1]

**[추정] 구현 절차 —** 직교 비교 실험에서만 ① 고정 카메라 방향의 right/up 좌표를 구한다. ② 화면 월드 높이를 `L`이라 정의하고 `q=L/H` 격자로 카메라 위치를 반올림한다. ③ 원래 위치와의 차이를 저장한다. ④ 스냅된 행렬로 렌더한다. ⑤ 반대 화면 오차로 표시 위치를 보정한다. 경계 노출을 막을 추가 렌더 여유 영역도 고려한다. 이 프로젝트의 원근 카메라를 직교로 바꾸자는 제안이 아니다. [O1] [P1]

**[추정·계산] 수치·비용 —** 최근접 반올림의 축별 위치 오차는 최대 `q/2`, 저해상도 화면에서는 반 픽셀이다. 위치 계산은 소수의 벡터 연산이지만 화면 보정에는 합성 처리와 여유 영역이 필요하다. 실제 추가 타깃 크기·ms는 미확인이다. [O1]

**[추정] 실패 사례 —** 원래 카메라 위치로 culling하고 스냅된 위치로 그리면 화면 가장자리의 물체가 누락될 수 있다. 색상·깊이·외곽선에 다른 보정을 적용하면 경계가 분리된다. 보정 출력의 bilinear 샘플링은 경계를 부드럽게 만들 수 있어, 저해상도 texel 이동과 최종 디스플레이 픽셀 이동을 구분해야 한다. [U2] [U4] [O1]

**[추정] 원근 적용 한계 —** 앞 절의 투영식에서 보듯 단일 격자와 단일 화면 오프셋은 서로 다른 깊이의 시차를 동시에 제거하지 못한다. 이 한계를 모든 다른 샘플링 기법의 불가능성으로 일반화하지 않는다. [U3] [P1]

**[추정] 원근에서 시험할 축소안 —** 주인공의 기준 깊이 `z0`에서만 `q(z0)`로 작은 카메라 평행 이동을 양자화해 근·원거리 떨림 변화를 비교할 수 있다. 회전·줌·전후 이동·지면 경사까지 고정된다고 주장해서는 안 된다. 오히려 카메라 이동이 계단식으로 느껴지거나 다른 깊이의 creep가 커지면 채택하지 않는다. [U3] [P1]

### 3.5 오브젝트 루트 스냅과 정점 스냅의 구분

**[사실]** ProPixelizer는 루트 기준으로 자식 장비의 픽셀 격자를 정렬하고, 각도 스냅도 장비처럼 중첩된 경우 루트에만 적용하도록 권한다. 별개 사례인 PSX Look 저자는 clip-space의 `xy/w`를 격자로 반올림하고 `w`를 다시 곱하는 정점 스냅을 wobble 표현으로 설명한다. 두 처리는 목적이 다르다. [P1] [V1]

**[추정] 루트 스냅 구현 —** ① 논리·충돌 위치와 시각 위치를 분리한다. ② 시각 루트의 화면 투영 위치만 정렬하고 같은 화면 이동을 부속 메시 전체에 공유한다. ③ 각 본을 독립 반올림하지 않는다. ④ 색상·깊이·노멀·ID·그림자에 사용할 행렬 차이를 검토한다. 원근에서는 루트의 깊이에서만 정렬되는 근사이며 관절 변형으로 변하는 실루엣은 남는다. [P1] [U3]

**[추정] 정점 스냅 구현 —** 비교용 셰이더에서 스키닝 이후 clip position의 화면 좌표를 저해상도 격자에 맞추고 깊이·`w`는 보존한다. 관련 패스에도 같은 변위를 적용해야 한다. 정확한 픽셀 중심·viewport·화면 Y방향·near-plane 처리는 그래픽 API별 검증 대상이며 이 문서에 컴파일 가능한 코드를 제시하지 않는다. [V1] [U5]

**[추정·계산] 수치·비용 —** 최근접 정점 스냅은 각 축 최대 반 픽셀의 위치 변화가 있지만, 서로 다른 정점이 다른 방향으로 움직이므로 모양 변화는 누적될 수 있다. 루트 처리는 물체 수, 정점 처리는 그리는 정점 수와 패스 수에 비례하는 연산을 추가한다. ms·허용 정점 수는 미확인이다. [V1] [U7]

**[사실] 실패 사례 —** PSX Look의 목적 자체가 카메라 이동 시 정점이 흔들리는 표현이다. [V1]

**[추정] 채택 한계 —** 리깅 캐릭터의 얇은 손·무기·관절에서 정점 스냅이 삼각형을 납작하게 하거나 실루엣을 튀게 할 수 있다. 본별 반올림은 손발 길이와 접점을 흔들 수 있다. 따라서 정점 스냅을 동작 가독성 개선의 기본값으로 두지 않고, 루트 정렬과 별도로 비교해야 한다. [V1] [P1] [A1]

### 3.6 명암 단계화와 시간적 필터 제한

**[사실]** Holland는 toon 조명과 최소한의 면 분할을 설명하며, 움직이는 태양의 그림자 깜빡임을 줄이기 위해 별도 처리를 했다. Dead Cells 원저자도 저해상도·AA 없는 셀 셰이딩을 사용했지만 픽셀 깜빡임은 해결하지 못했다고 밝혔다. [O1] [D1]

**[추정] 구현 절차 —** ① 피부·천·금속의 큰 명암 덩어리를 먼저 정한다. ② 연속 diffuse 값을 ramp로 단계화한다. ③ 작은 specular·노멀 디테일을 줄인 상태와 비교한다. ④ 그림자·림라이트·외곽선이 같은 위치에 과밀하게 쌓이지 않는지 본다. ramp 단계 수·specular 폭·그림자 설정의 적정값은 미확인이다. [O1] [O3] [A2]

**[사실] 필터 수치·실패 —** Unity 6000.6 문서의 TAA는 이전 색상 프레임과 motion vector를 이용하며, 빠른 물체와 대비가 큰 배경에서 ghosting이 생길 수 있다. MSAA는 삼각형 경계에 효과적이지만 specular·텍스처 같은 shader aliasing은 해결하지 않는다. [U6]

**[추정] 구현 기준·비용 —** 첫 비교에서는 픽셀 장면의 TAA·FXAA/SMAA·motion blur를 끄고 선·포즈의 원래 상태를 본다. 이후 필요한 효과만 따로 비교한다. 단순 ramp는 재질 연산이지만 그림자·별도 합성·시간 필터는 다른 비용이다. AA 해제만으로 충분한 가독성이나 성능을 보장할 수 없으며 ms는 미확인이다. [U6] [U7] [A2]

**[추정] 실패 사례와 원근 한계 —** 조명 경계의 작은 변화가 밝은 픽셀을 계속 켰다 끄면, 메시 실루엣이 안정되어도 동작이 산만하게 보일 수 있다. 멀리서 사라지는 팔·무기는 명암 단계 수를 늘려 복구할 수 없다. 디더를 쓰면 확대 비율에 따른 모아레까지 검토해야 한다. [P4] [U3] [O1]

### 3.7 Dead Cells의 제작 파이프라인과 실시간으로 가져올 부분

**[사실] 실제 절차·수치 —** Thomas Vasseur의 과정은 픽셀 모델 시트 → 3ds Max 모델·골격 → FBX → 사내 무AA 저해상도 렌더 → 프레임별 PNG·노멀맵 → toon 조명이다. 게임 내 높이 약 **50픽셀**은 사례 수치이며 대상 권장값이 아니다. [D1]

**[사실] 애니메이션 절차 —** 최소 키 포즈로 타이밍을 확정한 뒤 보강하며 공격은 pose-to-pose와 VFX를 활용한다. 포즈·시각 수정과 모델·동작 재사용이 장점이다. [D1]

**[사실] 잘못 옮기기 쉬운 수치 —** 원문의 **30fps**는 앞선 **ScarKrow** 설명이다. Dead Cells의 동작별 fps·골격/폴리곤 수·GPU 비용은 미확인이다. [D1]

**[추정] 실시간 적용 절차 —** PNG 베이크를 채택하지 않고, 같은 키 포즈·홀드·타이밍 수정 방식을 리깅 클립에 적용한다. 원근 게임 카메라의 저해상도 출력에서 먼저 판단하고 보간을 넣는다. 장비 교체·회전·조명 변화는 실시간의 장점으로 유지하되, 출력 픽셀의 품질을 별도로 검증한다. [D1] [A1] [U2]

**[추정] 비용·실패·원근 한계 —** 오프라인 프레임 출력은 방향·동작·장비 조합마다 이미지 관리 비용을 만들 수 있다. 실시간 방식은 그 대신 스키닝·그리기·외곽선 비용을 부담한다. 두 방식의 공수·메모리·ms 비교는 미확인이다. 고정 측면 프레임의 성공이 자유 원근 시점의 성공을 보증하지 않으며, 원저자도 깜빡임과 세부 표현의 손실을 남은 문제로 보고했다. [D1] [U3] [U7]

### 3.8 원근 안정화의 별도 연구: Texel Splatting

**[사실]** Dylan Ebert의 arXiv 원고는 고정 원점 cubemap의 위치·노멀·재질·ID를 texel별 shading한 뒤 월드 quad로 투영한다. animated geometry는 향후 과제여서 리깅 모델 검증 사례가 아니다. [T1]

**[추정] Unity 연구 절차 —** cubemap 캡처 → texel shading → quad 출력 → probe 전환/노출 면 보충을 별도 시험한다. 화면 효과 하나의 교체로 견적 내지 않는다. [T1] [U2]

**[사실] 수치·비용 —** 저자 장면은 면당 `384²` texel에서 iPhone 15/A16/mobile Safari **40fps**, RTX 4090 **4ms/프레임 미만**이다. eye/grid/previous 세 probe 중 eye는 매 프레임, 나머지는 교대 갱신한다. Unity·본 게임 재현값은 아니다. [T1]

**[사실] 실패와 한계 —** probe에 없던 면이 드러나는 disocclusion을 eye probe로 메우지만 shimmer가 남는다. 셀 크기는 안정성과 노출 면적의 절충이다. [T1]

**[추정] 판단 —** 즉시 채택보다 별도 연구 대상이다. Unity 이식 공수·메모리·애니메이션 품질은 미확인이다. [T1] [U2]

## 4. 동작이 뭉개지지 않게 하는 애니메이션 원칙

### 4.1 실루엣과 포즈를 렌더보다 먼저 확정

**[사실]** Riot의 애니메이션 교육 자료는 애니메이션을 시간에 걸친 포즈로 설명하며, 좋은 포즈·timing·spacing을 핵심으로 둔다. Riot의 clarity 문서는 캐릭터 식별에 실루엣을 가장 중요하게 보고 바라보는 방향도 실루엣만으로 읽혀야 한다고 설명한다. [A1] [A2]

**[추정] 구현 절차·수치 —** 실제 원근 카메라의 근·중·원거리에서 idle, 예비동작, 공격의 극점, 회복 포즈를 단색 실루엣으로 비교한다. 팔과 몸통 사이 공간, 무기 끝, 발의 접촉을 읽을 수 있게 포즈·비율·동작 평면을 조정한다. 허용 최소 간격·무기 두께·캐릭터 픽셀 높이는 미확인이다. 일반적인 최소 픽셀 수를 근거 없이 확정하지 않는다. [A1] [A2] [U3]

**[추정] 비용·실패·원근 한계 —** 카메라에서 보이는 포즈를 다시 잡는 제작 공수가 든다. 재질·폴리곤을 늘려도 포즈가 겹쳐 보이는 문제는 해결되지 않을 수 있다. 카메라를 향한 전후 베기는 투영상 이동 폭이 작아질 수 있으므로 옆 방향에서만 읽힌다고 통과시키지 않는다. 공수·가독성 개선치는 미확인이다. [A1] [A2] [U3]

### 4.2 예비동작 → 실행 → 회복, 키 포즈 중심 타이밍

**[추정] 구현 절차 —** 동작을 예비동작·접촉/실행·회복의 역할로 나누고, 각 상태가 구별되는 최소 키 포즈부터 만든다. 이후 필요한 구간에만 보간을 추가한다. 게임의 기존 공격 판정 시각에 시각 포즈를 맞추며, 보기 좋게 만들기 위해 판정 자체를 옮기는 것은 이 연구의 제안 범위가 아니다. [D1] [A1]

**[추정·계산] 수치 —** 표시율이 60Hz라면 한 표시 프레임은 약 `16.67ms`, 30Hz라면 약 `33.33ms`다. 이는 `1000/Hz` 계산이며 적정 공격 속도가 아니다. 해당 동작의 예고·접촉·회복 시간과 홀드 프레임 수는 미확인이다. 표시 프레임 수와 애니메이션 키 수, 게임 판정 틱을 별도 기록한다. [A1] [U9]

**[추정] 비용·실패·원근 한계 —** 전 구간의 균일한 보간이 극점 포즈를 약화시키거나 전부 홀드한 동작이 느리게 느껴질 수 있다. 키 수를 줄였다는 이유만으로 스키닝 비용이 비례 감소한다고 계산하지 않는다. 근거리에서 통과한 타이밍도 작은 원거리 실루엣에서 재확인해야 한다. ms·수정 공수는 미확인이다. [A1] [P3] [U3]

### 4.3 제한 프레임·stepped pose와 게임 시간의 분리

**[사실]** ProPixelizer의 stepped animation 도구는 키를 줄이고 보간을 None으로 설정한다. 문서는 animation tree의 블렌딩이 다시 중간 포즈를 만들어 flipbook 인상을 깨뜨릴 수 있다고 지적한다. 이것은 균일한 프레임 감소만으로 모든 동작이 좋아진다는 근거가 아니다. [P3]

**[추정] 구현 절차 —** 포즈 표시 시간만 `t_pose = floor(t × Fpose) / Fpose`로 표본화하는 실험을 하고, 이동·충돌·입력과 공격 판정 시간은 기존 기준을 유지한다. 빠른 극점 포즈를 건너뛰지 않도록 이벤트 시각과 홀드 구간을 먼저 설계한다. 양자화한 시각만 다시 평가할 경우 이벤트 누락·중복도 검증해야 한다. 적정 `Fpose`는 미확인이다. [P3] [A1] [U9]

**[추정·계산] 수치·비용 —** 균일한 floor 양자화의 포즈 지연은 `0 이상, 1/Fpose 초 미만`이다. 이 상한은 장면 품질 보증이 아니다. 평가 빈도를 줄여도 현재 메시를 계속 그리면 렌더 비용은 남는다. 평가/스키닝 절약량·메모리·제작 공수는 미확인이다. [P3] [U7]

**[추정] 실패와 원근 한계 —** 공격 전체를 단순 저속 재생하면 예고와 회복까지 함께 늘어날 수 있고, 표본화만 낮추면 접촉 포즈가 한 번도 표시되지 않을 수 있다. 원근에서는 전후 이동으로 크기가 변하므로 stepped pose만으로 픽셀 깜빡임을 제거할 수 없다. [D1] [P3] [U3]

### 4.4 블렌드·리샘플·압축이 키 포즈를 바꾸지 않는지 확인

**[사실]** Unity 6000.6의 transition은 Fixed Duration 여부에 따라 초 또는 원본 상태의 정규화 시간으로 기간을 해석한다. Animation Importer의 Resample Curves는 Euler 곡선을 프레임별 Quaternion 키로 재구성할 수 있고, 압축은 키를 줄일 수 있다. Rotation Error는 각도, Position/Scale Error는 비율 기준이다. [U8] [U9]

**[추정] 구현 절차 —** ① 원본의 핵심 포즈와 시각을 기록한다. ② 임포트 후 같은 시각과 앞뒤 시각을 비교한다. ③ 공격·피격 전환의 blend가 극점과 접촉을 없애는지 본다. ④ 문제가 생긴 클립에서만 전환 기간·리샘플·압축 오차를 조정한다. 포즈가 선명해야 하는 구간과 자연스러운 이동 전환을 구별한다. [U8] [U9] [P3]

**[추정] 수치·비용 —** 대상 transition 초, 압축 각도/비율 오차, 리샘플 주기는 미확인이다. 임시로 압축 Off 결과와 비교할 수 있으나 출시 기본값으로 단정하지 않는다. Unity는 Off가 파일·런타임 메모리를 늘리고 성능에 불리할 수 있다고 설명한다. 실제 절약량은 측정해야 한다. [U8] [U9]

**[추정] 실패와 원근 한계 —** 키 곡선을 stepped로 만들어도 상태 전환·레이어 혼합이 중간 포즈를 다시 만들 수 있다. 반대로 모든 전환을 없애면 보행·방향 전환이 튈 수 있다. 미세한 포즈 오차가 어느 거리에서 픽셀 경계를 넘는지는 카메라 투영에 의존하므로 클립 미리보기만으로 판정하지 않는다. [P3] [U8] [U3]

### 4.5 발 접촉·무기 궤적·VFX의 역할

**[추정] 구현 절차 —** 지지발과 시각 루트의 상대 위치, 손과 장비의 소켓 정렬을 함께 확인한다. 루트 스냅·포즈 홀드·이동 보간이 서로 다른 시점에 적용되지 않게 한다. VFX는 읽히는 포즈의 속도·접점·궤적을 보강하는 역할로 두고, 공격 방향을 포즈에서 먼저 식별할 수 있는지 확인한다. [P1] [D1] [A2]

**[추정] 수치·비용·실패 —** 발 미끄러짐 허용 픽셀 수·trail 지속시간·hit-stop 시간은 미확인이다. 보조 궤적은 추가 드로우·투명 overdraw를 만들 수 있어 별도 측정한다. 몸과 무기를 가리는 과한 효과, TAA 잔상, 접촉 이전에 뜨는 타격 효과는 가독성을 해칠 가설로 검토한다. 원근에서 멀어진 적의 포즈를 큰 VFX로 덮어 해결했다고 판정하지 않는다. [U7] [U6] [A2] [U3]

## 5. Unity 6000.6.7f1 URP 이식 순서와 비용 모델

**[사실]** Unity 6000.6은 `ScriptableRenderPass.RecordRenderGraph`에서 입력·출력을 선언하고 `SetRenderFunc`에서 그리기 명령을 구성하는 방식을 설명한다. `UniversalResourceData`로 프레임 자원을 얻고 `UseTexture`·`SetRenderAttachment`로 의존성을 선언한다. `AddRenderPasses`는 카메라마다 호출된다. [U2]

**[추정] 후속 구현 순서 — 아래는 아직 실행하지 않은 설계다.** [U2] [U7]

1. **[추정] 기준 확인:** 설치 URP 버전, Render Graph 활성 여부, Forward/Deferred, 카메라 출력 타깃과 해상도, AA·후처리·그림자·투명 머티리얼의 조건을 기록한다. 대상 API는 해당 설치 패키지에서 다시 확인한다. [U2] [U6]
2. **[추정] 가장 작은 경로:** 같은 원근 카메라의 불투명 모델을 저해상도로 그리고 Point 정수 확대한다. 먼저 외곽선 없는 기준을 만든다. [U4] [U2]
3. **[추정] 입력 일치:** 깊이·노멀을 요청하고 실제 생성 패스를 확인한다. 별도 override material을 쓰는 경우 기존 변형·노멀맵이 빠질 위험이 있으므로 모델의 color/depth/normal/ID가 같은 변형을 반영하는지 확인한다. [U7] [O3]
4. **[추정] 선 추가:** 먼저 깊이/ID 실루엣, 그다음 내부 노멀 선을 비교한다. 같은 입력 텍스처를 읽고 동시에 출력 대상으로 덮는 설계 대신 별도 출력과 명시적 의존성을 둔다. [P2] [U2]
5. **[추정] 합성 순서:** 불투명 → 외곽선 → 투명/VFX → 확대 → UI를 첫 비교안으로 삼는다. 물 굴절·투명 장비·앞뒤 가림에는 다른 순서가 필요할 수 있다. 비용과 정확성을 보고 조정하며 이 순서를 확정 사양으로 취급하지 않는다. [U2] [O1] [O3]
6. **[추정] 카메라/클립 분리:** 기준을 보존한 비교에서 루트 스냅, 기준 깊이 카메라 스냅, stepped pose를 하나씩 평가한다. 원근 카메라의 회전·줌을 직교로 치환하지 않는다. [P1] [P3] [T1]

**[사실] 비용 원칙 —** Unity는 불필요한 패스·색상/깊이 복사를 줄이고 기존 자원을 이용하도록 권한다. 현재 픽셀만 필요한 경우의 input attachment 최적화도 설명한다. [U7]

**[추정]** 이웃을 읽는 외곽선에는 그 최적화를 그대로 적용할 수 없다. 화면 해상도 감소만으로 그림자·추가 패스까지 같은 비율로 빨라졌다고 결론 내리지 않는다. [U7]

**[추정·계산] 메모리 견적 예시 —** 가상 구성으로 색상 입력/출력 각 RGBA8 4바이트, 인코딩한 노멀 RGBA8 4바이트, 깊이 R32 4바이트, ID R8 1바이트를 모두 따로 둔다면 `17×W×H`바이트다. `320×180`은 979,200바이트(약 0.934MiB), `640×360`은 3,916,800바이트(약 3.735MiB)다. 이는 **URP 실제 배치가 아닌 가정 계산**이다. HDR·MSAA·depth/stencil·그림자·history·정렬·중간 타깃과 Render Graph aliasing에 따라 달라진다. 지원 포맷·실제 peak GPU 메모리는 미확인이다. [U2] [U7]

**[추정] 인력·성능 견적 경계 —** 저해상도 출력만 하는 경로보다 변형 일치·ID 관리·투명 합성·시간 안정화를 함께 해결하는 경로가 더 많은 검증을 요구할 가능성이 높다. 사람/일 단위 공수와 GPU ms는 근거가 없어 제시하지 않는다. Texel Splatting 저자 수치를 이 경로의 비용으로 대입하지 않는다. [U2] [U7] [T1]
