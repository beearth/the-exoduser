제작자는 본인 작업 중 실제 이미지·영상 프레임을 직접 열고 후보와 대조한다. 파일/출처/직접 확인 시점이 연결되지 않거나 열리지 않는 항목은 미확인으로 남기고 확보할 다음 자료를 기록한다. 메모리 키·글 요약·다른 담당의 과거 열람만으로 본인의 시각/동작 검수를 대신하지 않는다. 사용자 스크린샷도 구도·초점·재질·조명·정보 계층의 참고이며 해당 작품의 고유 캐릭터·문양·UI 자산·배치를 복제하지 않는다.

### UI 레퍼런스의 공통 원칙 (해당 화면의 최신 승인 계약이 우선)

아래는 UI 구도 분석의 출발점이다. 보스·맵·캐릭터에 얇은 테·특정 폰트·색 수를 일괄 강제하지 않으며, 같은 UI라도 최신 화면별 확정안과 다르면 확정안을 적용하고 근거를 적는다.

1. **큰 메인 이미지 + 깔끔한 UI.** 장면(키아트·무대·캐릭터 전신)이 화면의 주인공이고, UI는 적고 얇고 모양이 같다.
2. 판·테는 없거나 아주 얇다(1px 헤어라인 + 양 끝 작은 마디). 글자를 장면 위에 바로 올린다.
3. 강조색은 한 가지. 선택된 것만 밝힌다.
4. 위계는 3단: 칭호(작고 넓은 자간) / 이름(크게) / 부제(작게).
5. 같은 모양의 부품을 적게 반복한다(버튼·판·카드 테·제목 띠가 한 벌).
6. 글꼴은 가는 명조(Hahmlet 300, 사용자 선택), 숫자·영문은 Cinzel 계열.
7. 메인 이미지는 살아 움직인다(앞·중간·먼 층이 따로 움직임, 멀리서 무언가 일어나는 신호).
8. 비운 화면일수록 남은 요소의 재질이 살아 있다(균열·마모·음각·주조). 평면 글자는 쓰지 않는다.

## 2. 분해표 — 만들기 전에 레퍼런스를 숫자로 뜯는다

같은 해상도(1600×900 또는 1920×1080)로 레퍼런스를 놓고 현재 작업에 적용되는 항목을 기존 브리프·보드에 적은 뒤 착수한다. 아래 숫자는 측정 방법의 예시이며 공통 상수가 아니다. 보스·캐릭터는 체형·실루엣·재질·리그/동작의 해당 LOCK 항목을 대신 쓴다. 미술 판정을 숫자로 대체하지 않는다.

| 속성 | 레퍼런스 측정값 | 우리 목표값 |
|---|---|---|
| 메인 이미지가 차지하는 면적 | 예: 75% | |
| UI가 차지하는 면적·위치 | 예: 하단 중앙 18% | |
| 테 두께·색 | 예: 1px, 금빛 45% 투명 | |
| 제목·본문 글자 크기·굵기·자간 | 예: 44px/300/0.12em, 15px/400 | |
| 색 수와 실제 색값 | 예: 3색 #dfd6c2 / #a49373 / 강조 #b3261e | |
| 명암 대비(밝은 곳 대 어두운 곳) | 예: 장면 중간톤, UI 판 72% 검정 | |
| 여백 | 예: 좌우 8%, 요소 간 24px | |
| 움직임 | 예: 안개 0.2px/f, 불씨 층 3개 | |
| 재질 | 예: 금속 음각 로고, 판은 무지 | |

## 3. 나란히 비교 — 보여 주기 전에 반드시 한다

1. 결과를 **실제 게임 화면 안에서** 캡처한다(단독 렌더·확대 PNG만으로 판정하지 않는다).
2. 레퍼런스와 같은 크기로 좌우에 붙인 비교 이미지와 1x 크롭을 만든다. 새 PC 출력은 `I:/EXODUSER-Storage/<역할>/<실행ID>/compare_*.png`, Mac은 현재 승인된 해당 호스트의 산출물 경로다. 2026-10-29 22시 정정에 따라 PC Unity 작업본·Library·DOTNET_CLI_HOME·UPM 캐시는 NTFS(G:/exoduser-wt 우선·확인한 E: 차선)에 두며 H5/docs·비교 출력·원본 보관은 계속 I:다. 전체 화면 비교와 같은 화면상 크기의 대상 비교를 구분하고 카메라·노출·배경 차이를 적는다.
3. §2 표의 각 속성마다 **같음 / 작은 차이 / 큰 차이**를 적는다.
4. 합의한 품질 특성의 미해결 큰 차이나 핵심 결함이 남으면 **최종 채택용 완료본으로 제출하지 않는다.** EXODUSER의 의도적인 세계관·형태·상징 차이는 복제해서 없애지 않는다. 가장 큰 실제 결함을 고치고 다시 검수한다.
5. 결함·진행·비용/도구 차단 보고는 위 조건과 무관하게 사실대로 보고한다. FAIL이나 미검증을 숨기며 계속 만드는 것을 막는다. 사용자가 시안을 요청하면 현재 평가 범위와 결함을 명시해 보여준다. 최종 후보는 비교 이미지와 속성별 판정을 함께 제시한다.

## 5. 금지 (어설픔의 직접 원인)

- 레퍼런스를 열어 보지 않고 기억·요약으로 만드는 것
- CSS 선·사각형·마름모·그라데이션으로 원화가 필요한 테·버튼·문장을 대신하는 것
- 의미 없는 장식(눈 고리·연꽃·뿔 해골), 로고 일부를 잘라 반복한 문장
- 첫 결과를 비교·평가 범위·결함 표시 없이 최종 완료본으로 내는 것. 사용자가 요청한 중간 시안은 현재 판정과 함께 제시한다.
- 평균색·PASS 수치로 화면 판정을 대신하는 것
- 이식 계약을 임의로 바꾸거나, 반대로 승인된 맵·보스 리모델의 표현을 과거 웹 외형 1:1로 제한하는 것
- 판정 없이 "디자인 완료"라고 쓰는 것 → 판정 못 했으면 **"기능만 완료, 디자인 미검수"**

## 8. 통합·인수와의 연결

- 기능 검사·oracle·컴파일·Player·시각·동작·청취·원격 반영은 별도 증거다. 정지 렌더로 동작을, 스튜디오 렌더로 실제 아레나 가독성을, 파일/파라미터로 음질을 PASS하지 않는다.
- 기능과 시각 회귀가 없는 RETOUCH의 기술 통합은 현행 통합 정책을 따른다. 실제로 거절된 FAIL 아트·확정 LOCK 위반·필수 사용자 선택 대기는 자동 채택하지 않는다. 분리 가능한 기능 변경은 소유 담당이 별도 후보로 기술/통합 조건을 충족한 범위만 처리하고, 실패 아트를 같은 변경에 끼워 넣지 않는다.
- 제작자 직접 검수와 별도 검수자의 확인을 구분한다. 검수자가 부재하면 현행 정책이 허용하는 자체 판정의 주체·범위를 적되 독립 검수라고 보고하지 않는다.
- 담당이 실제 증거로 직접 판정하고 상위는 필요한 표본·핵심 결함을 확인한다. 판정자 부재를 이유로 기존 허용된 기능 통합을 무기한 묶어 두지 않는다. 핵심 결함은 FAIL이며, RETOUCH는 AAA가 정한 평가 범위의 정체성·큰 형태가 성립한 국소 수정이다. 부분 형태 PASS를 제품 전체 PASS로 승격하지 않는다.
- 자동화는 새 후보/새 실패/새 완료 근거가 생긴 범위만 검수한다. 같은 화면·같은 SHA를 주기마다 다시 평가하거나 원인을 모르는 동일 빌드를 반복하지 않는다. 자동화 등록·문서 작성은 디자인 개선 증거가 아니다.
