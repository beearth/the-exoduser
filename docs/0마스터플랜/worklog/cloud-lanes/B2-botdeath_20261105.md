### 레거시/리모델 경로 주의

- 이번 로그의 bossSpin/bossMultiDash는 현재7기술 표와 섞어 분석하면 안 되는 레거시 계열 상태다. 원본 영수증에 리모델 플래그 자체가 없으므로 실행 플래그를 완전히 소급 확정하지는 않는다.
- `Core/DruidTelegraph.cs:74`는 `!Remodel`이면 빈 목록을 낸다. 따라서 봇에 DruidTelegraphs 읽기만 추가해도 레거시 실행에서는 여전히 예고 목록이 비어 있을 수 있다. **빈 API 목록을 “실제 화면 예고 부재”로 판정하면 안 된다.** 기존 레거시 본체 자세/효과 경로는 별도다.
- 보고용 코드 결함은 실제 두 빌드의 동일 봇 소스로 확인했다. 더 최신 기준 브랜치의 리모델 전용 개선을 과거 6사망의 원인 증거로 거꾸로 적용하지 않았다.

- 집중 검사2: 후보 구현 후 **16개 중1실패** — `heartbeat moves into safe circle, not farther away`.

- 사용자 규칙 “같은 검사2회 실패”에 따라 구현/재검사 중단. 두 번째 실행 이후 알고리즘 수정·검사 재실행·봇 연결·Unity 실행 없음. 실패 후보는 `unity/Tools/botdeath-tests/BossThreatCandidate.cs`로 이동해 보존했고 Runtime에서 제거했다. csproj의 참조 경로만 격리 위치로 맞췄으며, 해당 이동 뒤 다시 실행하지 않았다.

- .NET의 기존 Core `EnemyAi.cs:87` CS0219 경고2개는 원문 그대로다. 컴파일/Player/화면 검증 PASS로 확대하지 않는다.

## QA 하니스에서 사망 순간을 기록하는 방법 — 다음 구현 제안

아래는 **제안이며 이번 커밋에는 구현하지 않았다.** 사망 순간 보스 상태와 치명타 원인 기술을 다른 필드로 둔다.

1. 기존 fullrun의 수동 `FixedUpdate()` 호출 직전/직후에 QA 전용 최근120틱 ring buffer를 쌓는다. tick, playerState/위치, 보스 S/CurMove/RmMoveId/St2, 리모델 여부, 예고 목록의 MoveId/Kind/Shape/Total/Remaining/Live, 해당 입력 키/공격/회피 목표를 기록한다. 읽기만 하며 Core 타이밍/HP/피해 코드를 고치지 않는다.
2. `PlayerDown` 분기에서 **2.7초 대기·캡처·재시도 전에** `deathIndex=receipt.deaths+1`, retryIndex, tick과 현재 보스 상태/기술, 최근 buffer를 `boss-deaths.jsonl`에 즉시 저장하고 fullrun.json의 deathDetails에도 넣는다. 재시도 때 buffer를 비워 다른 목숨의 표본을 섞지 않는다. 대기 후 움직인 보스 상태를 사망 원인으로 기록하지 않는다.
3. 필드 이름은 `bossStateAtDeath`/`bossMoveAtDeath`/`incomingCandidates`와 `fatalSourceMove`/`causeConfirmed`를 분리한다. 기존 읽기 가능한 HurtCount·LastHurtAmount와 자원 snapshot의 전후 변화, 살아 있는 투사체/위험 후보를 같이 기록할 수 있지만, 이 역시 발사한 이전 기술·중독 등을 자동 확정하지 못한다. 유일한 실제 source event와 연결하지 못하면 fatalSourceMove는 빈 값, causeConfirmed=false로 둔다.
4. (가)/(나)를 나누려면 Core API 예고 수, `teleView.DrawnEntries` 같은 **제출된 view 항목 수**, 봇이 인식한 위험·선택한 입력·최종 입력을 함께 남긴다. view 수>0도 픽셀 가시성은 아니다. 실제 예고 부재 확정에는 같은 tick Mac 캡처 대조가 필요하다.
5. 입력 증거는 `FullRunControlInputs.Apply`·`BossArenaReviewInputs`·parryG2 override **이후**, 실제 `InputState.Change`에 전달한 키를 기록한다(`NativeGame.FullRunQa.cs:275` 근처). 방어 목표를 계산했지만 마지막 override가 지운 경우를 봇 무대응과 구분한다. 별도 가상 체력/무적·강제 위치·강제 클리어를 추가하지 않는다.

## Mac 재실행 인자 / 인계

지금은 후보가 연결되지 않았고 위 trace도 미구현이므로 **아래 인자는 기존 재현용이며 수정 검증 완료를 뜻하지 않는다.** 다음 담당이 QA 수정·trace를 통과시킨 후 정확한 새 SHA를 R1/Mac에 넘긴다. 이번 턴은 Mac 재실행을 기다리지 않는다.

```text
--unity-fullrun-qa --remodel3d -qa-width 1920 -qa-max-ticks 54000 -qa-retries 5 -output <Mac-QA-고정-출력폴더>
```

- 현재 코드가 실제 읽는 인자만 적었다. `--qa-boss-trace` 같은 미구현 인자를 실행 가능하다고 적지 않는다.
- Mac 담당의 기존 공용 무창·무음·QA 세이브 격리 실행기와 같은 초기 세이브/장비 조건을 유지한다. 인자 없이 사용자 실제 세이브를 열지 않는다. 과거 clean unity/main/combo4와 새로운7기술 리모델 실행을 별도 증거로 남긴다. 필요하면 기존 실행 인자 전문을 원본 Player 로그/빌드 영수증과 함께 보관한다.
- 최소 산출물: 새 SHA/리모델 여부/실제 인자, 6회 각각 deathIndex·deathTick, 즉시 사망 snapshot과 직전120틱, API/view/봇 최종입력, 기술명 확정 여부, 같은 tick 무음 화면. 박동 안전원 경계 회귀를 먼저 해결하고 같은 검사 재시도 규칙은 새 배정에서 따른다.
- 완료 기준 판정: **분류 보고·미확인 사망표·QA 기록 방법·Mac 인자 제안은 충족. 봇 수정은 중단/미완료이며 각 사망의 실제 치명타 기술과 (가)/(다) 원인은 미확인.** 이 제출로 난이도/Core를 수정하거나 게임 품질 PASS라고 보고하지 않는다.
