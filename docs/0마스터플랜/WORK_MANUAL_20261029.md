## 5. Git

- `git add -A` 금지. 변경 전후 `git diff --cached --name-status`와 `git diff --name-status`를 분리 확인한다. 정확한 자기 경로만 `git add -- <경로>`로 올리고 staged diff를 검수한다. 공유 INDEX에 타인 변경이 있으면 그것을 포함하지 않는 경로 지정 커밋 또는 격리 작업 트리를 사용한다.
- 강제 push·reset --hard·rebase로 공유 이력을 다시 쓰지 않는다. push 거절 시 fetch 후 새 원격 부모·겹친 경로를 확인하고 자기 격리 작업 트리에서 정상 통합한다. 공유 G:에 자동 pull/merge하지 않는다.
- `git stash` 금지(저장소 전체가 공유해서 남의 stash가 섞인다).
- `git gc`·`repack`·`prune` 금지(10-27 팩 손상 이력).
- 커밋 메시지 끝에 작성자 줄을 붙인다. Claude는 `Co-Authored-By: Claude …`, Codex는 `Co-Authored-By: Codex (PC) …`.
- 타인 미커밋 작업은 담당자의 명시적 인수 범위·원작성자·원백업·새 복구 지점을 확인한 경우에만 통합한다. 미인수 WIP/HOLD를 복사해 끼워 넣지 않는다.
- 정상 push 후 `git ls-remote origin <정확한 ref>`로 원격 SHA를 읽어 커밋과 대조한다. 로컬 커밋, 원격 작업 브랜치, 줄기 반영, 실행본 갱신은 별도 상태다. 인증 실패는 공식 credential helper 또는 승인된 connector로 처리하고 비밀값을 출력하지 않는다.

## 6. 실행·디스크·프로세스

- 자동 실행은 화면 없이, 소리 없이 한다(브라우저 headless+mute, Unity batchmode·숨은 데스크톱·AudioListener 0). 창·보조 모니터를 띄우지 않는다.
- 산출물을 start/explorer로 열지 않고 경로만 보고한다.
- 백그라운드에서 `python -`처럼 stdin을 기다리는 명령 금지. 스크립트는 파일로 넘긴다.
- 끝난 Unity 플레이어가 "종료됨"인데도 남아 폴더를 잡는 일이 있다. 그러면 폴더를 교체하지 말고 바로가기 대상을 바꾼 뒤, 재부팅 후 정리한다.
- Playwright·브라우저 임시 프로필은 쓰고 나서 지운다.

## 7. 판정·완료·보고

| 상태 | 뜻 |
|---|---|
| 완료 | 기능 동작 + 디자인 톤 일치 + 1x 가독성 + (Unity) 바로가기 빌드에 반영 |
| 기능만 완료, 디자인 미검수 | 화면 판정·비교 이미지가 없음 |
| 병합만 됨 / 빌드 미확인 | 사용자가 열어 볼 빌드가 없음 |

완료는 해당 작업의 합격 조건을 모두 충족한 범위에만 쓴다. docs 전용 작업은 내용·참조·변경 경로 검수와 Git 반영 상태를 보고한다. 기능 검사, 시각·청취·동작 판정, Player/실플레이, 원격 줄기, 배포·Set Live의 증거를 각각 기록한다. 적용되지 않는 항목은 사유와 함께 해당 없음으로 쓴다. 미검증을 PASS로 올리지 않는다.

- 보고에는 브랜치·SHA, 검증 근거(빌드 run·스모크·oracle), 비교 이미지 경로, 남은 일, 사용자 확인 항목을 넣는다.
- 총괄 보고는 CTO 한 곳으로 보낸다. 사소한 진행 알림은 보내지 않는다.
- 사용자에게 묻는 것은 새 방향, 유료 지출, Steam Set Live·외부 게시·배포, 되돌릴 수 없는 삭제뿐이다. 나머지는 담당이 정하고 결과만 보고한다. 같은 질문을 반복하지 않는다.
- 확인 항목은 `USER_CONFIRM.md`, 결함은 `FINDINGS.md`에 한 줄씩 추가만 한다(덮어쓰기 금지).

### 총괄 인수와 재작업

1. 총괄은 목표·우선순위·소유 범위·의존성·판정 기준을 정하고 해당 역할의 제작 담당에게 구체적인 한 단위를 배정한다. 제작자가 제출한 것과 총괄이 직접 확인한 것을 구분한다.
2. 제작자는 후보를 실제로 보고 결함을 수정한다. 총괄은 같은 SHA·후보·실행 조건을 확인해 PASS / RETOUCH / FAIL 또는 미검증으로 판정한다. 근거는 [AAA 기준의 현행 합격선](AAA_QUALITY_STANDARD_20260927.md#2026-10-29-실행-규칙--시각-완성도와-재작업-책임)을 따른다.
3. RETOUCH/FAIL은 결함 위치·원인·수정할 항목·담당·다음 확인 조건을 남긴다. 같은 핵심 결함이 같은 방법으로 두 후보 연속 FAIL이면 제작 단계를 되돌려 방법을 바꾼다.
4. 소스·검수·docs·복구 지점을 마친 뒤 승인된 다음 미완료 작업을 진행한다. 새 방향·필수 권한·유료 지출·외부 게시 등 사용자 결정이 필요한 부분만 남긴다. 새 변경·새 증거 없이 같은 검사·빌드를 반복하지 않는다.

### 공통 완료 보고 양식

```text
- 작업 ID / 담당 / 목표:
- 변경: <정확한 코드·에셋·docs 경로와 동작 변화>
- 기준: <SSOT·레퍼런스·웹 source SHA/앵커>
- 검수: <조건·명령 또는 실행기·결과·로그/캡처/영상/청취 근거>
- 판정: 기능 <결과> / 시각·음향·동작 <결과> / 실게임 <결과>
- 반영: 로컬 <branch·SHA> / 원격 <ref·조회 SHA> / 실행본 <경로·빌드 SHA>
- 남은 결함·미검증 / 재작업 담당·다음 조건:
- 다음 승인 작업 / 꼭 필요한 사용자 결정:
```

문서·증거는 기존 팀 SSOT·작업 보드에 기록하고 [총괄 관리 대장](PROJECT_MANAGEMENT_MASTER.md)에 담당 범위·근거·남은 일·반영 단계를 갱신하거나 인계한다. 같은 결과를 새 문서로 반복 작성하지 않는다.
