# 작업 매뉴얼 v4 — 지옥의 길

2026-11-03 KST 개정. 사용자: "메뉴얼을 잘 만들어야 해, 계속 가져가야 할 퀄리티의 기준이 될 거니까."
이 문서가 모든 담당(Claude 총괄·Codex 레인·Mac)의 **품질 기준이자 작업 순서**다. 우선순위는 사용자 최신 지시 → 이 매뉴얼 → 분야 SSOT·DESIGN LOCK 순이다. 통과 조건 표는 [품질 기준](WORK_QUALITY_STANDARD_20261029.md), 등급 정의는 [AAA 기준](AAA_QUALITY_STANDARD_20260927.md)에 있다.

## 0. 왜 다시 썼나 — 2026-11-03 실패 기록

게임을 만든 지 5개월이 넘었는데, 사용자 말로 결과물이 "다른 사람들보다 엄청 느리고 구리다".
1. **맵:** 1-1을 웹의 걸을 수 있는 큰 덩어리 그대로 두고, 그 위를 후보 C1~C17로 17번 꾸몄다. 길·벽·순서·랜드마크 같은 **구도 설계는 한 번도 하지 않았다.** 그래서 무엇을 올려도 휑했다.
2. **캐릭터:** 4프레임 안팎의 저해상도 그림을 크게 확대해서 썼다. 그림은 블록처럼 깨졌고, 동작에는 **움직임의 출처가 없었다.**
3. **제작법:** AI 2D 그림을 3D 지형에 펴 발랐고(질감 늘어남·누운 그림), Blender 코드로 소품을 깎았다(감자 바위·벌레 같은 고목). 남들이 쓰는 검증된 방법을 먼저 알아보지 않았다.
4. **운영:** 레인을 열 개 넘게 벌여 놓고 반쯤 하다 멈췄다. CTO 세션이 끝나자 레인이 전부 죽었고, 네 시간 동안 아무도 몰랐다. 바탕화면 실행본과 맵 바로가기는 하루 종일 바뀌지 않았다.

아래 규칙은 모두 이 네 가지가 다시 일어나지 않게 하려고 있다.

## 1. 핵심 원칙 10

1. **사용자가 여는 곳이 바뀌어야 진척이다.** 웹 3333, 바탕화면 `지옥의 길 (Unity)`, 후보 바로가기가 그날 바뀌지 않았으면 그날 진척은 0이다. 문서·커밋·테스트 통과는 진척이 아니다.
2. **설계 먼저, 꾸미기 나중.** 구도(맵)·실루엣과 동작 출처(캐릭터)·타이밍(VFX)이 레퍼런스처럼 읽히기 전에는 재질·소품·디테일을 올리지 않는다. 설계가 틀린 것을 꾸미기로 덮지 않는다.
3. **남들이 어떻게 만드는지 먼저 배운다.** 새 분야나 두 번 막힌 분야는 착수 전에 실제로 잘 만든 사례 3개의 도구·순서·결과를 조사한다. 그 가운데 검증된 방법을 고르고, 근거를 브리프에 적는다. 마케팅 문구가 아니라 결과물로 판단한다.
4. **§3의 검증된 제작법만 쓴다.** 금지 방법은 쓰지 않는다. 표에 없는 방법은 CTO가 시험 하나로 확인한 뒤 표에 올리고 쓴다.
5. **"레퍼런스 | 결과"를 같은 크기로 나란히 놓은 비교가 없으면 미완이다.** 큰 차이가 남아 있으면 사용자에게 내지 않는다.
6. **눈에 보이는 개선 하나를 끝까지 한다.** 빌드와 바로가기 반영까지가 끝이다. 동시 레인은 8개 이하로 두고, 각 레인은 하루 안에 사용자가 여는 곳 하나를 바꾼다.
7. **같은 방법으로 두 번 실패하면 방법을 바꾼다.** 후보 이름을 바꿔도 같은 핵심 결함이면 같은 실패로 센다. 한 라운드가 가장 큰 차이를 줄이지 못했으면 실패다.
8. **총괄은 직접 본다.** 레인 보고를 옮기기만 하지 않는다. 결과 이미지와 영상을 열어 레퍼런스 옆에서 판정한 뒤 전달한다.
9. **좋은 결과는 즉시, 전체 현황은 매시간 보고한다**(§6). 변화가 없으면 "새 완료 없음"과 정체 원인을 그대로 쓴다.
10. **승인된 일은 다시 묻지 않고 끝까지 한다.** 새 비용, 배포·외부 게시, 되돌릴 수 없는 삭제, 레퍼런스 밖 새 방향만 사용자에게 묻는다. 정해진 목표 안의 선택은 총괄이 정하고 결과만 보고한다.

## 4. 레인 운영 — 총괄(CTO)

- **레인 하나에는** 브리프 파일 하나, 작업본 하나, REPORT.md 하나(맨 위 3줄: ① 사용자가 여는 곳에 반영된 SHA·경로 ② 지금 관문과 판정 ③ 다음 일)를 둔다. 같은 파일을 쓰는 레인을 둘 두지 않는다.
- **테스트베드도 최신 게임 위에서 만든다.** 레인 브랜치는 하루를 시작할 때 unity/main(웹은 main)을 먼저 병합한다. 작업은 하루 한 번 이상 자기 브랜치에 커밋하고 push한다. 미커밋 상태로 하루를 넘기지 않는다. 테스트베드에서 통과한 것은 플래그 뒤에 두고 그날 바로 줄기에 합쳐서, 바탕화면 실행본에서도 열리게 한다(2026-11-03: 맵 테스트베드가 137커밋 뒤라 로비가 옛것이었고, 맵 코드가 하루 넘게 미커밋이었다).
- **동시 레인은 8개 이하로 둔다.** 방법이 대체되었거나 하루 동안 사용자가 여는 곳을 바꾸지 못한 레인은 멈추고, 원인을 적은 뒤 다시 짠다.
- **Codex 레인은 총괄 세션의 자식 프로세스다.** 세션이 끝나면 함께 죽는다. 세션을 시작하거나 다시 열 때마다 `codex.exe` 목록과 REPORT 갱신 시각을 확인하고, 죽은 레인은 `codex exec resume <세션 id>`로 이어 간다. 레인 목록과 세션 id는 `I:\EXODUSER-Storage\codex-takeover\LANES.md`에 둔다(`CTO_STATE.json`은 별도 자동화가 혼자 쓰는 파일이라 건드리지 않는다).
- **Unity 실행은 공용 실행기** `I:\EXODUSER-Storage\unity-jobs\bin\exo-unity.ps1`만 쓴다(에디터 1개·Player 2개, 무창·무음·세이브 격리). 작업본 안의 옛 사본은 부르지 않는다.
- 환경 문제(드라이브·권한·디스크·실행기·대기열)는 30분 안에 총괄에게 올린다. 하루 종일 대기 기록만 쌓지 않는다.
- **사용자 프로그램(Dota 등)이 켜져 있어도 멈추지 않는다.** 사용자 프로그램은 종료하지 않는다. 메모리가 모자라면 낮은 설정이나 순차 실행으로 진행한다. 실행기의 최소 여유치(exo-unity 6GB·buildloop 8GB)만 대기 조건이다.

## 5. 웹·Unity 동시 진행과 최신판 자동 갱신

- 웹(main)은 Steam EA·데모로 나가는 현행판이고, Unity(unity/main)는 출시 목표판이다. 둘을 함께 진행한다. 인게임 월드(웹 2.5D 레이어, Unity 3D)만 다르다. **화면·반응·소리·흐름·움직임은 100% 같다.** 웹에서 UI·UX·소리를 바꾸면 같은 작업 단위 안에서 Unity에도 넣고, 보고에 두 SHA를 함께 적는다. 대조표는 `docs/engine/UNITY_WEB_UX_PARITY_LEDGER.md`다.
- 사용자가 여는 실행본은 예약 작업이 자동으로 최신으로 맞춘다. 손으로 갱신하지 않는다.

| 대상 | 기준 | 자동 갱신 | 확인 |
|---|---|---|---|
| 웹 3333 | origin/main | `EXODUSER_LatestWeb3333`(5분): `G:\exoduser-wt\latest-web` fast-forward | `I:\EXODUSER-Storage\tools\latest-web-refresh\refresh.log` |
| 바탕화면 Unity | origin/unity/main | `EXODUSER-Unity-BuildLoop`(30분): 빌드 → 무창 GPU 스모크·UI 겹침 검사 통과 시 `I:\EXODUSER-Storage\unity-latest\build` 교체 | `I:\EXODUSER-Storage\unity-latest\status\index.html` |

- 반영했다는 사실만으로 실행본이 바뀌었다고 보고하지 않는다. 다음 주기 뒤 위 확인 위치에서 SHA를 보고 보고한다. 예약 작업이 멈추거나 검사에서 막히면, 그것을 그날의 첫 결함으로 고친다.

| 결과 보고 | 의미 있는 완료나 실패가 나오면 즉시 | ① 사용자가 볼 수 있게 바뀐 것 하나 ② 확인 위치(바로가기·비교판·SHA) ③ 남은 가장 큰 차이 하나와 다음 행동 |
| 시간별 보고 | 매시간, 한국어 4~6줄 | 완료 → 진행 → 정체 원인·조치 → 다음. 변화가 없으면 "새 완료 없음" |
| 사용자 결정 | 필요한 단계에서 한 번 | 결정할 것 하나와 비용. 같은 질문을 반복하지 않는다 |

과정·원인 분석을 길게 쓰지 않는다. 컴파일·테스트 통과를 시각 PASS나 전달 완료로 대신하지 않는다. 문서 갱신은 게임 진척과 따로 보고한다.

## 7. 공통 안전 규칙

- **점·잔점 금지:** 그림·영상·합성 어디든 3x 크롭에서 점 0개를 확인해야 쓸 수 있다. 그레인·노이즈를 더하지 않는다.
- **슈퍼와이드:** 모든 화면을 16:9·21:9·32:9에서 성립시키고, 검수에 1920×1080과 3840×1080을 항상 넣는다. 검은 판·블러 채움은 금지다.
- **무창·무음:** 자동 실행(브라우저·Unity 에디터·Player)은 창을 띄우지 않고 소리를 끈다. 결과 이미지·폴더를 자동으로 열지 않는다.
- **Git:** H5·공통 docs는 main, Unity는 unity/main, Godot은 동결이다. 정확한 자기 경로만 stage해서 정상 commit하고, 비강제로 반영한다. push 전 expected SHA, push 뒤 원격 SHA를 대조한다. `git add -A`·force·stash·reset·gc·prune·history 재작성은 금지다. 타인 WIP는 건드리지 않는다.
- **작업 공간:** Unity 작업본·Library·캐시는 NTFS(G: 우선)에 둔다. H5·docs 작업본은 I:에 둔다. 빌드·캡처·로그·다운로드는 `I:\EXODUSER-Storage\` 아래에 둔다. C:에는 큰 산출물을 두지 않는다. 백그라운드에서 stdin을 기다리는 명령(`python -`)은 쓰지 않는다. 상세 경로 정책은 [빌드·백업 정책](../13출시·마케팅/BUILD_BACKUP_POLICY_20261001.md)을 따른다.
- **비용:** 유료 생성은 사용자 승인 범위 안에서만 하고, 예약과 실제 차감을 `I:\EXODUSER-Storage\codex-takeover\SPEND_LOG.md`에 적는다. 연결과 예산은 [MCP·API 공통 목록](../API연결_가이드.md)에 있다. 키·토큰은 출력하지 않고 Git에 넣지 않는다. 로그인·계정 생성·결제는 사용자가 직접 한다.
- **사용자 실행본·세이브:** 사용자 창과 서버를 자동으로 재시작하지 않는다. 사용자 세이브는 읽기만 한다.

과거 운영 이력과 상세 사례는 [총괄대장](PROJECT_MANAGEMENT_MASTER.md#2026-10-30-v3-정리와-이전-상세자료)에 둔다.
