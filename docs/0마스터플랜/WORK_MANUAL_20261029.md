# 작업 매뉴얼 v3 — 지옥의 길

최신 운영 정정: 2026-11-02 KST. 사용자 “잘됀거있음 보고하고 별로면 다시하고 계속해”와 시간별 작업보고를 적용한다. 아래 정정된 규칙이 과거 무보고·20분 주기·기승인 배포 재확인 문구보다 우선한다.
## 핵심 10줄
1. **사용자가 여는 곳이 바뀌어야 진척이다.** 웹 확인 서버와 바탕화면 `지옥의 길 (Unity)`가 그날 안에 바뀌지 않았으면 그날 진척은 0이다.
2. **문서만 바꾼 작업은 진척으로 세지 않는다.** 새 규칙 문서는 만들지 않고, 기존 문서를 고칠 때도 줄 수를 늘리지 않는다.
3. **화면 작업은 "레퍼런스 | 결과"를 같은 크기로 나란히 놓은 이미지가 없으면 미완**이다. 큰 차이가 남아 있으면 사용자에게 내지 않는다.
4. **원화가 필요한 곳을 CSS·벡터 도형으로 대신하지 않는다.**
5. **한 번에 눈에 보이는 개선 하나를 끝까지 한다**(빌드·바로가기 반영까지). 여러 개를 반쯤 하다 멈추지 않는다.
6. **판정자가 없는 대기에 걸어 두지 않는다.** 만든 쪽이 증거와 함께 판정하고 병합한다. 막히면 원인이 다른 길로 바꾼다.
7. **환경 문제(드라이브·권한·디스크·실행기)는 30분 안에 CTO에 올린다.** 하루 종일 HOLD 기록만 쌓지 않는다(10-29 exFAT 사례).
8. **같은 방법으로 2번 실패하면 방법을 바꾼다.** 같은 시도를 다시 반복하지 않는다.
9. **좋은 결과는 실제 작업물·검수 범위·확인 위치와 함께 즉시 보고한다.** 미흡하면 결함과 다음 수정을 알리고 재작업한다. 전체 현황은 변화가 없어도 매1시간 한국어 4~6줄로 보고한다(§5).
10. **기승인 작업은 재확인 없이 검수·docs·정상 commit/push·실제 전달까지 끝낸다.** 새 비용·권한·범위 밖 결정·되돌리기 어려운 사용자 데이터 변경만 필요한 단계에서 확인한다.

이 10줄은 이 매뉴얼의 다른 절보다 우선한다. 사용자 최신 지시·상위 지침·분야 LOCK·기존 소유/통합 권한은 지킨다. 문서 반영은 게임 개선 진척과 별도로 보고한다.

## 1. 개선 하나를 끝내는 순서

1. 최신 사용자 목표와 기존 보드에서 승인된 한 단위만 고른다. 현재 데모 단계·보호된 writer·보류 범위를 확인하고 새 팀/작업본을 중복 생성하지 않는다.
2. 기존 브리프에 목표 장면/플레이 경험, 직접 본 레퍼런스, 현재 가장 큰 차이, 제작 방법, 가장 이른 실물 판정, 합격/중단 조건을 짧게 적는다. 저품질 시안 양산을 기획으로 대신하지 않는다.
3. 담당·host·정확한 소유 파일/함수·source SHA·선행 의존·기승인 비용·허용 행위·다음 행동·출력 경로를 확인한다. 타인 WIP·공유 INDEX·세이브를 보존한다. [MCP·API 공통 목록](../API연결_가이드.md)에서 연결·기간별 크레딧 예산을 확인하고 예약·실제 차감을 같은 내부 원장에 기록한다.
4. 경로·Git 연결/common-dir·이동 완료·실행 source를 확인한 뒤에만 fetch하고 branch/HEAD·원격 SHA·INDEX/WORK를 분리 확인한다. 깨진 링크·이동 중 경로만 해당 쓰기를 보류한다.
5. 제작 → 제작자 직접 검수/수정 → 필요한 표본/교차 검수 → 권한 있는 담당의 정상 통합 → 빌드/사용자 실행본 갱신 → 실제 열리는 경로 확인까지 마친다.
6. 제작자의 증거 있는 자체 판정을 허용하는 기존 게이트를 적용한다. 별도 검수자가 없다는 이유로 묶어 두거나 자체 검수를 독립 검수로 보고하지 않는다.
7. 좋은 결과는 실제 작업물과 판정 범위를 보고하고 전달까지 닫은 뒤 다음 승인 단위를 진행한다. 미흡하면 결함·담당·다음 수정물을 기록하고 재작업·재검수한다. 같은 핵심 방법 2회 실패는 증거 보존 후 방법 전환. 막힌 항목은 30분 안에 CTO에 원인·증거·대안을 올리고 충돌 없는 독립 승인 작업을 이어간다.

## 3. 검수·통합·실행본

- [품질 기준](WORK_QUALITY_STANDARD_20261029.md)의 분야별 표와 나란히 비교를 적용한다. 판정은 [AAA 목표·등급](AAA_QUALITY_STANDARD_20260927.md)에 따른다.
- **점·잔점이 보이는 그림·영상은 사용 불가다.** 생성·업스케일·합성·샤프닝 후 3x 크롭에서 점 0개를 확인해야 제출할 수 있다. 그레인·노이즈 추가는 금지한다(2026-11-02 사용자 확정).
- 화면 작업은 착수 단계부터 16:9·21:9·32:9를 함께 설계하고, 검수 캡처에 1920×1080과 3840×1080을 항상 넣는다. 전체 화면 그림은 확장판을 같이 만든다(검은 판·블러 채움 금지, 2026-10-31 사용자 확정).
- 기능·시각/동작/청취·실게임·원격·사용자가 여는 실행본은 별도 증거다. UPM 성공·컴파일·정지 렌더·커밋·메시지 수신을 플레이/디자인 완료로 올리지 않는다.
- FAIL 아트는 채택하지 않는다. 회귀 없는 분리 가능한 RETOUCH 기능 통합은 기존 권한대로 진행하고 품질 상태·다음 수정은 남긴다.
- 동일 테스트는 첫 실패 뒤 원인 수정·재실행 한 번까지, 다시 실패하면 그 단위를 중단한다. 같은 제작법의 핵심 아트 두 후보 FAIL은 제작 단계/방법을 바꾼다. 이름만 바꾸어 카운터를 초기화하지 않는다.
- H5/공통 docs는 main, Unity는 unity/main, Godot은 동결 줄기다. 정확한 자기 경로만 stage·정상 commit하고 비강제 반영한다. push 전 expected SHA, push 뒤 원격 ref SHA를 대조한다.
- 공유 add/reset/stash/force/gc/prune·자동 서버 재시작·사용자 창 종료·무단 이동/삭제·권한 변경은 금지한다. 막힌 검사나 권한을 우회하지 않는다.
- PC Unity 동시 한 개·실행기 잠금·무창/무음·세이브 격리를 지킨다. 실행본을 갱신한 사실과 사용자가 실제로 보는 화면/플레이 검수를 구분한다.
- 전체 보스 리마스터 등 승인 범위는 유지하되 현재 데모 목표의 순서·허용된 의존 작업만 배정한다. 세부 절차는 해당 시스템 SSOT를 따른다.

## 4. heartbeat — 실제 전달과 시간별 작업보고

**"마지막 확인 뒤로 사용자가 여는 빌드가 바뀌었나?"**

- 중앙 exoduser-cto 한 개·현재 채팅·매1시간 ACTIVE를 유지한다. 실제 담당 상태·오류·최근 도구와 근거를 먼저 확인하고 현재 단계·소유·선행 의존성을 대조한다. 새 자동화·watchdog·팀·writer·작업본을 만들지 않는다.
- 실제 source/빌드 SHA·사용자 바로가기/서버 경로·새 결과를 마지막 처리 cursor 이후와 비교한다. 원격 커밋이나 파일 시각만으로 사용자 빌드 변경을 선언하지 않는다.
- 바뀌지 않았고 막힌 담당이 있으면 다른 원인의 승인 작업 한 건으로 돌린다. 같은 환경 재시도·새 담당·중복 writer로 바꾸지 않는다.
- active·writer 점유·pending·동일 dispatchKey이면 중복 지시 0. 승인된 전달은 native send_message_to_thread 우선. 전송/수신과 실제 새 도구 착수를 구분한다.
- 현재 상태·후속·실패 횟수는 I:/EXODUSER-Storage/codex-takeover/CTO_STATE.json과 기존 보드에서 읽고 root만 쓴다. 시험 당시 RUNNING을 현재 상태로 복사하지 않는다.
- 사용자가 시간별 보고를 명시 요청했으므로 매 실행 §5의 4~6줄 작업보고를 남긴다. 변화가 없으면 “새 완료 없음”, 정체 원인·마지막 실제 도구 시각/경과·이번 조치를 보고한다. 좋은 결과·새 실패·필수 결정은 인수 즉시 별도 보고하며 과거 완료를 새 완료처럼 반복하지 않는다.
- 기승인 작업은 기존 소유자·선행·안전 조건 안에서 구현·검수·docs·정상 commit/push·실제 전달까지 이어간다. 무조건 자동 병합하거나 타 lane/OS 작업을 재가동하지 않는다. 빌드·실행은 담당·공식 순서·자원·무음·저장 보호를 확인하며 자동화 등록·실제 실행·사용자 보고 전달은 각각 구분한다.
- 상세 운영·실패 대응·협의·시험 이력은 [총괄대장](PROJECT_MANAGEMENT_MASTER.md#2026-10-30-v3-정리와-이전-상세자료)에만 둔다.

## 5. 결과 즉시 보고와 시간별 전체보고

좋은 결과는 실제 이미지·영상·실행 경로와 변경 내용·직접 검수 범위를 보여준다. 미흡하면 결함을 숨기거나 완료로 올리지 않고 수정 담당·다음 산출물·재검수 방법을 적는다. 사용자의 답변 대기를 이유로 승인된 독립 작업을 멈추지 않는다.

| 구분 | 시점·필수 내용 |
|---|---|
| 결과 보고 | 의미 있는 완료·실패 인수 즉시. 작업물/확인 위치, 바뀐 점, 기능·실화면·시각 판정, 미반영·미검증, 후속 조치 |
| 정기 보고 | 매1시간, 한국어 4~6줄. 완료 → 진행 → 정체 원인/마지막 실제 도구 시각·경과/이번 조치 → 다음 담당·작업·확인할 결과 |
| 변화 없음 | “새 완료 없음”과 현재 정체·이번 해소 조치 보고. 과거 성과를 이번 완료로 포장하지 않음 |
| 반영 단계 | 소스/후보 원격 → 빌드 → 같은 앱 Player/M1 → 원본 1x/실게임 → 공통 → 웹 공개·일반 앱·바탕화면 실제 전달을 각각 명시 |
| 컨펌 | 새 선택이 필요한 결과만 항목별 확인. 기승인·컨펌 단위는 반복 질문 없이 필요한 검수·정상 commit/push·전달 수행 |

개별 결과는 아래 세 항목을 기본으로 하고, 정기 전체보고에는 완료·진행·정체·다음의 4~6줄 형식을 적용한다.

```text
① 변화: 사용자가 볼 수 있게 바뀐 한 가지와 실제 검수 범위.
② 확인 위치: 실행 경로/바로가기·비교 이미지·필요한 SHA/근거.
③ 남은 가장 큰 차이 하나: 구체 결함과 다음 행동/꼭 필요한 결정.
```

최종 채택용 완료본과 결함/차단 보고를 구분한다. 컴파일·수락 메시지·자동 테스트를 시각 PASS나 전달 완료로 대신하지 않는다. 연결 장애는 확인 불가 시각과 마지막 확인 상태로 보고하며 현재도 작업 중이거나 중단됐다고 추정하지 않는다. 문서 갱신은 게임 개선 성과와 별도로 보고한다.
