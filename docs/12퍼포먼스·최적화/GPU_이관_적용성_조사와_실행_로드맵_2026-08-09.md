## 1. 전제와 현재 아키텍처

이 프로젝트는 Unity 프로젝트가 아니다. 단일 `game.html` 기반 2D 게임으로, Canvas2D 명령을 WebGPU 또는 WebGL2로 전송하는 하이브리드 렌더러를 사용한다. 따라서 Unity 전용 API인 SkinnedMeshRenderer, VAT 베이커, MaterialPropertyBlock, VFX Graph, APV, Forward+, Addressables를 직접 도입할 수 없다.

렌더 백엔드는 WebGPU → WebGL2 → Canvas2D 폴백 순서이며, 플랫폼별 경로를 유지해야 한다. 특히 Mac에서는 WebGL2 텍스처 업로드가 BGRA8 swizzle 병목을 일으킬 수 있으므로 WebGPU 경로를 WebGL2로 강제 전환하지 않는다.

| 현행 구현 | 코드 기준 | 의미 |
|---|---|---|
| 적 스프라이트 아틀라스 | `_atlasE`, `_atlasEUV`, `_getEFrame()` | 스켈레탈 애니메이션이 아닌 프레임 기반 2D 애니메이션 |
| 적 GPU 인스턴싱 | `_ensGLCpu` + `_ens8GLCpu: Float32Array`, `_drawEnemyInstanced()` + `_drawEnemy8DirInstanced()` | 레거시 `_atlasE`와 주력 8방향 `_ch8Atlas` 적을 WebGL2 인스턴스로 전송. 8방향은 idle/walk 방향별 16개 텍스처 버킷으로 배치 |
| 가산 VFX GPU 인스턴싱 | `_vfxGLCpu: Float32Array`, `_flushVfxGL()` | 최대 256개 가산 블렌드 VFX를 텍스처 단위로 배치. 동일 텍스처 256개 격리 WebGL2 검증 완료 |
| 렌더링 준비 | 부트 `[WARMUP]` 블록, `_warmupEnsAtlas()` | 파이프라인과 다수 스프라이트의 첫 사용 비용을 로딩 중 분산 |
| CPU 보호 장치 | AI 티어링, 공간 해싱, 뷰포트 컬링, 오브젝트 풀/순환 버퍼 | 렌더와 게임플레이 로직을 분리해 유지 |

## 2. Unity 최적화 항목별 판정

| 제안 항목 | 판정 | 이 프로젝트의 대응 |
|---|---|---|
| VAT + GPU Instancing | VAT는 비적용, 인스턴싱 적용 확대 | 2D 스프라이트 아틀라스의 프레임 UV가 VAT 목적을 대체한다. WebGL2 `drawArraysInstanced`가 레거시 적과 주력 8방향 적 모두에 적용되며, 8방향의 idle/walk 프레임은 텍스처 버킷별 UV로 전송한다. |
| 여러 VAT 클립 통합 / MaterialPropertyBlock | 대체 적용 완료 | `_ensGLCpu`와 `_vfxGLCpu` 사전 할당 배열이 인스턴스 속성 버퍼 역할을 한다. Unity 재질 API는 사용하지 않는다. |
| VFX Graph + GraphicsBuffer | 조건부 적용 | Unity VFX Graph 대신 WebGPU StorageBuffer + compute + instanced quad로 구현 가능하다. 1,000개 이상인 **순수 시각** 파티클에만 후보이며, 충돌/AI 결과를 GPU에서 CPU로 매 프레임 읽어오지 않는다. |
| APV | 비적용 | 3D GI/Lightmap UV 문제를 해결하는 Unity 기능이다. 이 게임에는 2D 타일/캔버스 조명 경로가 맞는다. |
| Forward+ | 비적용 | 3D 실시간 다중 라이트 컬링용이다. 현재 2D 조명에 도입하면 비용과 복잡도만 증가한다. |
| Terrain → Mesh | 비적용 | Unity Terrain이 없고, 맵은 타일 캐시·스트리밍 뷰포트 합성으로 렌더한다. |
| PBR 채널 패킹 / 동적 브랜칭 | PBR 패킹은 비적용, 아틀라스화는 조건부 | Diffuse/Normal/Metallic 재질이 없다. 다만 동일 블렌드·동일 텍스처 그룹의 투사체/VFX는 측정 후 아틀라스화하여 flush를 줄일 수 있다. |
| Cold Start / PSO Trace | 웹식 대체 적용 | Chrome/NW.js의 실제 첫 렌더를 기준으로 프로파일한다. Unity PSO Trace는 없으며, 파이프라인 준비 시점은 드라이버/브라우저에 따라 첫 사용까지 지연될 수 있다. |
| 로딩 화면 강제 스폰 웜업 | 적용 후보 1순위 | 게임 상태를 바꾸지 않고 대표 텍스처·블렌드 모드·파이프라인을 실제 1px draw 후 flush한다. 첫 투사체 히치가 재현될 때만 구현한다. |
| 공격 티켓 시스템 | 절대 금지 | 핵슬래시의 동시 공격 쾌감을 제한하므로 프로젝트 규칙과 성능 보고서 모두에서 금지한다. |
| Zero-allocation | 상시 적용 | 핫패스에서 배열/Set/Map/클로저/객체 리터럴의 신규 할당을 피하고 풀·링 버퍼·typed array를 재사용한다. |
| Addressables / 강제 언로드 | 웹식 대체만 허용 | 맵 단위 lazy load, LRU 캐시, 실제 동적 `ImageBitmap`/오디오 리소스의 수명 관리만 검토한다. 브라우저에 Unity의 `UnloadUnusedAssets()` 대응물은 없다. |
| 전방위 오브젝트 풀링 | 적용 완료, 감사만 지속 | 파티클·투사체·임팩트·VFX·데미지 텍스트는 풀 또는 순환 버퍼를 사용한다. 정적 HUD는 DOM 재사용이 적절하다. |

## 3. 확인된 첫 실행 히치 가설

2026-05-23 실측에서 첫 투사체 렌더는 46ms의 1회성 스파이크가 남아 있었다. 당시 부트 웜업은 `_glMainProg`를 흰 `fillRect`로 실제 draw했지만, 투사체 이미지 텍스처를 바인딩한 draw는 수행하지 않았다.

### 3.1 현재 코드와 과거 가설의 차이 (2026-08-09 재확인)

`_BULLET_IMGS`는 `_warmupEnsAtlas()`의 오프스크린 2D 워밍업 큐에 포함되지만, 현재 `pProjs[]`의 공용 런타임 렌더 소스는 아니다. 플레이어 투사체는 속성/스킬에 따라 아래 경로로 갈린다.

| 현재 런타임 경로 | 조건 | 대표 소스 |
|---|---|---|
| 석궁 화살 | `normalBow && _bowArrowReady` | `_bowTinted[]` 또는 `_bowArrowImg` |
| 업화선/악의구 | `fireBeamProj` / `fireball` | `_FB_IMG` / `_MO_IMG` 스프라이트시트 |
| 일반 마법 투사체 | `magic` | `_drawShardSprite()` 또는 `_drawBoltSprite()`; 실패 시 절차 렌더 |
| 그 외 특수 투사체 | 속성별 분기 | Canvas 경로·도형·별도 스프라이트시트 |

따라서 `_BULLET_IMGS[0]` 하나만 강제 바인딩하는 구현은 현재 첫 투사체 경로를 보장하지 않는다. 단계 0에서 실제로 스파이크를 만드는 경로를 식별한 뒤, 해당 텍스처·블렌드·draw 조합만 웜업한다.

### 원인 가설

첫 투사체의 경로는 셰이더 링크만이 아니라 **실제 이미지 텍스처 업로드/바인딩 + 텍스처 샘플링 draw**까지 처음 사용한다. 따라서 흰색 쿼드 draw만으로는 이 경로의 드라이버 JIT 또는 텍스처 준비 비용을 모두 선행할 수 없다.

### 검증 조건

1. Cold Start에서 첫 기본 투사체 발사 시점의 `proj` 구간과 전체 프레임 시간을 기록한다.
2. 같은 환경에서 로딩 중 대표 투사체 이미지의 1×1 draw와 flush를 실행한다.
3. 첫 투사체 스파이크가 기준 대비 의미 있게 감소하고, 게임 진입 전 시각 출력·게임 상태·세이브 데이터가 바뀌지 않을 때만 채택한다.
4. 효과가 없으면 추가 추측 수정 없이 변경을 되돌리지 말고, 측정값과 원인을 이 문서에 기록한 뒤 다음 후보를 분리 진단한다.

### 단계 1 구현 결과 — 8방향 적 GPU 배치 (2026-08-09)

| 항목 | 구현값 |
|---|---|
| 대상 | `e._mob8dir && e._mobCh` 일반 적 |
| 버퍼 | `_ens8GLCpu: Float32Array(16 × 512 × 9)`, `_ens8GLCounts: Uint16Array(16)` — 시작 시 1회 할당·매 프레임 재사용 |
| 인스턴스 한도 | 적 본체 512개 + 이동 walk 오버레이 512개 = 최대 1,024 스프라이트; 16개 버킷은 저장 공간만 분리 |
| 드로우 | idle 방향 8 + walk 방향 8, 활성 텍스처만 `drawArraysInstanced` 호출 (최대 16회) |
| 좌표/프레임 | 기존 Canvas와 동일한 `col/row/cell`, walk `framesPerMob`, `floor(_walkDist/128)` 규칙 |
| 중복 방지 | 성공한 적만 `e._ensGLMode=1`; 기존 일반 적 Canvas 본문은 `let _eDrew=!!_ensGLQueued`로 건너뜀 |
| 유지 경로 | 보스·구울·슬라임·상태/공격 시각효과·WebGL 미준비/큐 거절은 기존 Canvas 경로 |
| 회귀 테스트 | `test/eightDirEnemyInstancing.test.js` — 16버킷 사전할당, 1,024 스프라이트 한도, Canvas 중복 방지, 성능 로그 정적 계약 4건 통과 |
| 브라우저 검증기 | `tools/verify_eightdir_enemy_instancing_browser.mjs` — 격리된 headless Chrome WebGL2에서 실제 `_prepEnemyInstanced()`/셰이더 호출을 512마리 규모로 검증 |
| 실기기 계측 | `_DEBUG_PERF=true`에서 30프레임마다 `e8:인스턴스수@버킷드로우수` 출력. 예: `e8:500@8`은 500개 스프라이트를 8개 활성 방향/애니메이션 텍스처 draw로 처리했다는 뜻 |
| 512마리 격리 스트레스 결과 | headless Chrome/SwiftShader에서 512 적 × idle+walk = 1,024 스프라이트가 16 버킷 draw로 처리됨. `_prepEnemyInstanced()` CPU 구간 1.7~3.2ms(4회), `GL.getError()=0`, 페이지 오류 0건 |
| VFX 격리 스트레스 결과 | headless Chrome/SwiftShader에서 동일 텍스처 additive VFX 256개가 1회 `drawArraysInstanced`로 처리됨. 큐+제출 CPU 0.3~0.6ms(3회), `GL.getError()=0`, 페이지 오류 0건 |

초기 브라우저 감사에서 15/15가 `_mobCh=1`이라 기존 인스턴싱이 0이었던 병목을 이 경로로 해소했다. 실사용 GPU의 프레임 시간 전후 비교와 시각 비교는 별도 성능 프로파일 세션에서 수행한다. 이 작업 환경에서는 사전 존재 Chrome/Node 프로세스 때문에 구현 후 독립 headless 검증이 완료되지 않아, 사용자 프로세스를 종료하지 않고 정적 회귀 테스트까지만 완료했다.

### 후속 실행 검증 기록 (2026-08-09)

| 항목 | 결과 |
|---|---|
| 로컬 서버 응답 | `http://127.0.0.1:3333/game.html?...` → HTTP 200 |
| 페이지 초기화 | headless Chrome에서 `_useGL=true`, `_ensGLMode=true`, 페이지 오류 0건 |
| 격리 GPU 배치 호출 | 실제 WebGL2 컨텍스트에서 512개의 임시 8방향 이동 적을 `_prepEnemyInstanced()`에 전달 → `queued=512`, `sprites=1024`, `draws=16`, CPU 1.7~3.2ms(4회), `GL.getError()=0`, 페이지 오류 0건 |
| 테스트 캐릭터 완료 대기 | `_startTestChar()`의 스킨·맵·청크·캐시 준비가 자동화 제한 124초 내 `G.on=true`에 도달하지 않아 미완료 |

| 판정 | WebGL2 초기화 실패나 페이지 예외는 아니다. 적 스폰 및 `_dbgEns8GL` 실측은 로컬 NW.js/Chrome 수동 세션 또는 더 긴 전용 CI에서 재측정 필요 |

자동화가 시간 제한을 초과했으므로 사용자 Chrome/Node 프로세스는 종료하지 않았으며, 이 결과만으로 추가 렌더 코드 변경이나 임의 워밍업을 진행하지 않는다.

다만 `tools/verify_eightdir_enemy_instancing_browser.mjs`의 격리 검증은 부트 완료를 기다리지 않아 같은 환경에서 성공했다. 이 검증은 임시 텍스처를 사용하므로 실스킨 텍스처의 전체 로드 시간·실기기 GPU 시간·전체 500마리 게임 프레임 시간을 대체하지 않는다. 대신 새 8방향 인스턴스 큐·idle/walk 1,024 스프라이트 한도·WebGL 텍스처 업로드·셰이더 드로우 및 상태 복원이 실제 브라우저에서 오류 없이 동작함을 보장한다.

`tools/verify_vfx_gl_instancing_browser.mjs`도 같은 방식으로 부트 완료와 독립해 VFX 큐·additive 블렌딩·제출 경로를 검증한다. 이 값은 한 텍스처 배치의 CPU 제출 비용이며, 여러 VFX 텍스처가 섞이면 `_queueVfxGL()`의 텍스처 전환 flush 수가 증가한다. 따라서 VFX Graph/GraphicsBuffer 같은 새 GPU 시스템 도입은 1,000개 이상 시각 파티클 또는 텍스처 전환이 실제 병목으로 확인될 때만 재검토한다.

## 5. 단계 0 기준선 결과 (2026-08-09)

### 측정 환경

| 항목 | 값 |
|---|---|
| 서버 | 로컬 `server.cjs`, 포트 3333 |
| 브라우저 | 새 headless Chrome 프로세스, 1280×720 |
| 진입 | `game.html?test=1&testchar=1&stage=1` |
| 렌더 백엔드 | WebGL2 (`_useGL=true`, `_useGPU=false`) |
| 측정 대상 | 게임 시작 후 생성한 마법 `pProj` 1개가 포함된 첫 `drawP()` 호출 |
| 결과 | 첫 `drawP()` 0.6ms, 29프레임 최대 0.6ms |

### 관찰값과 판정

- 이 환경에서는 2026-05-23에 기록된 첫 투사체 46ms 스파이크가 재현되지 않았다.
- 부트 중 경고는 `envVig` 54.0ms, `bonfire` 22.3ms의 1회성 후처리 스파이크였다. 게임 플레이의 첫 투사체와 혼동하지 않는다.
- **후속 반영(2026-08-10)**: `bonfire` 첫 사용 업로드는 `_WQ_BONFIRE_BARRIER` 전용 ProxyX 워밍업으로 로딩 단계로 이관했다. 현재 원인은 맵 스트리밍이 아니라 시작 보호막 이미지의 첫 GPU 텍스처 업로드였다.
- **envVig 재검증(2026-08-10)**: 현 코드의 `G._dvgCvs`는 현재 stage·width·canvas 크기와 일치한다. 과거 캐시 객체 불일치 가설은 폐기하며, 실제 Cold Start GPU 제출 스파이크가 재현될 때만 전용 웜업을 검토한다.
- 이 측정은 새 브라우저 프로세스를 사용했지만 OS/드라이버 캐시를 삭제한 진정한 Cold Start나 NW.js/실사용 GPU의 PSO trace는 아니다. 또 `drawP()` CPU 시간은 GPU 제출 이후의 비동기 드라이버 작업을 완전히 대변하지 않는다.

**결정: 단계 2의 투사체 텍스처 웜업 구현은 보류한다.** 현재 기준선이 게이트를 통과하지 못했으므로, 특정 텍스처를 임의로 웜업하는 코드를 추가하지 않는다. 실사용 NW.js에서 첫 투사체 히치가 재현되거나 성능 봉인 해제 조건을 만족할 때만, 해당 경로의 텍스처·블렌드·실제 draw를 분리 계측하여 다시 시작한다.

## 5.1 SFX 부트 대기 제거 (2026-08-10)

Cold Start 코드 조사에서 `_loadAudioBuffers()`가 AudioContext `suspended` 상태를 최대 10초 기다린 뒤 `_sampleFiles` 전체를 데스크톱에서 직렬 fetch/decode하고, 부트가 이를 `await`하는 것을 확인했다. 이는 GPU/PSO 문제가 아닌 명시적인 부트 임계경로다.

| 변경 | 값 |
|---|---|
| 부트 호출 | `await _loadAudioBuffers()` → `void _loadAudioBuffers()` |
| 동시성 | `_AUDIO_LOAD_CONCURRENCY=4`의 제한 워커 |
| 중복 요청 | 기존 `_audioLoadPending` 공유 |
| 폴백 | 미준비 샘플은 기존 lazy load/무음 경로, 게임 시작 차단 없음 |
| 회귀 | `test/audioBootLoading.test.js` 2건 통과 |

headless 테스트 캐릭터 전체 부트는 이 변경 후에도 124초 안에 `G.on=true`에 도달하지 않았다. 따라서 맵·청크·캐시 생성이 별도 병목으로 남아 있으며, 이 결과를 오디오 변경 실패나 GPU 문제로 해석하지 않는다.

**후속 반영(2026-08-10)**: 다음 Cold Start 단계 계측을 구현했다. URL `?perf=1`(또는 콘솔 수동 설정)으로 `_DEBUG_PERF=true`인 경우 `showBootLoading()`부터 `hideBootLoading()`까지 `setBootLoading()`의 진행률·단계명·직전 단계 대비 시간과 누적 시간을 `[BOOT PERF]` 한 줄로 출력한다. 게임 시작 순서나 대기 시간은 바꾸지 않으며, `test/bootStageTimingDiagnostics.test.js`와 `tools/verify_boot_stage_timing_browser.mjs`로 계측 게이트/실제 Chrome headless 출력을 검증한다. 다음 작업은 이 로그에서 가장 긴 단계 하나가 실측된 뒤에만 그 단계로 한정한다.

**첫 실측 및 후속 반영(2026-08-10)**: Chrome headless·SwiftShader 표준 Cold Start 표본에서 `_preloadAssets()`의 첫 완료까지 약 1.47초, 부트 로딩 화면 종료까지 약 2.43초가 측정됐다. 묶음 안의 원인을 추측하지 않도록 `?perf=1`에서 500ms 초과 개별 요청만 `[BOOT ASSET SLOW]`로 기록한다. 이 계측은 에셋 수·압축·순서를 바꾸지 않는다.

**판정(2026-08-10)**: 같은 표본에서 거의 모든 프리로드 항목이 약 1.43~2.38초로 함께 기록됐다. 이는 병렬 요청의 대기열 시간이 각 항목에 포함된 결과이며, 특정 파일 하나를 병목으로 확정할 근거가 아니다. Cold Start 대기는 부트 화면 안에서 발생하고 이동 중 프레임 스파이크와 별개이므로, 이 결과만으로 에셋 축소나 제거를 진행하지 않는다.

**후속 반영(2026-08-10)**: 정상 플레이에서 프레임이 느려졌을 때 `[drawP]`·`[S6-SUB]`·`[S7-*]`·`[POST SPIKE]` 콘솔 출력이 추가 비용을 만들지 않게 `_DEBUG_PERF` 게이트로 통일했다. URL `?perf=1`에서만 기존의 상세 진단을 유지하며, 렌더·VFX·맵 로직은 변경하지 않는다.

**후속 반영(2026-08-10)**: 이동 중 전체 프레임이 끊기지만 개별 draw 구간이 원인이 아닐 때를 위해, `?perf=1`에서만 34ms 초과 원시 rAF 간격을 `[FRAME HITCH]`로 기록한다. 500ms 출력 제한과 함께 직전 update/draw EMA, 스트리밍 청크·GPU 워밍업 대기 수를 보여 준다. 기존 50ms 물리 클램프는 유지한다.

**후속 반영(2026-08-10)**: 같은 디버그 실행에서 `PerformanceObserver`의 `longtask` 항목을 한 번만 구독한다. `[LONG TASK]`가 `[FRAME HITCH]`와 함께 나오면 게임 렌더 구간 밖의 메인 스레드 점유도 원인 후보로 분리할 수 있다. 미지원 환경은 무동작이며 일반 실행에는 등록하지 않는다.

## 6. 절대 제약

- 공격 티켓을 구현하지 않는다.
- 화려함, VFX 수, 게임 밸런스, 일반 몬스터 동시성으로 성능을 해결하지 않는다.
- Mac 문제를 이유로 WebGPU를 WebGL2로 강제 전환하지 않는다.
- 게임 루프 핫패스에 `new`, `splice`, `filter`, `forEach`, `Date.now()`를 추가하지 않는다.
- GPU 계산 결과를 매 프레임 CPU로 전체 readback하지 않는다.
- 각 변경은 테스트 우선(TDD), 실제 브라우저 확인, 성능 수치 기록 후 다음 단계로 진행한다.
