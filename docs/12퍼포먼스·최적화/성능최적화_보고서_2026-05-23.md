## 1. 요약

성능 측정용 로깅 시스템 강화, 셰이더 프리워밍 코드 47줄 추가, 다수의 옛 가설 검증 및 무효화 작업 진행.
최종 격전 폭타 비용이 **21ms → 17ms (약 4ms 개선)**.

**출시 합격선 도달:**
- 평상시 **140fps 이상**
- 700마리 **60fps**
- 격전 폭타 **55fps**

이후 추가 진단 시도는 **봉인**하며, 실제 게임이 깨지는 명확한 신호가 나타나기 전까지 성능 작업을 중단한다.

### 3.4 후속 계측 추가 (2026-08-09)

주력 8방향 몬스터가 WebGL2 인스턴싱으로 이관되면서, `_DEBUG_PERF=true`의 30프레임 로그에 `e8:인스턴스수@버킷드로우수`를 추가했다. 예를 들어 `e8:500@8`은 500개의 8방향 스프라이트 레이어가 8개의 활성 텍스처 버킷 draw로 처리되었음을 뜻한다. 이는 측정 전용 카운터이며 게임 로직·몬스터 동시성·공격 빈도를 변경하지 않는다. 실사용 NW.js/GPU의 전후 프레임 시간은 별도 프로파일 세션에서 기록한다.

### 3.5 SFX 프리로드 부트 분리 (2026-08-10)

SFX 전체 decode가 부트 완료를 막던 구조를 제거했다. `_sampleFiles`는 최대 4개 동시 워커로 백그라운드 fetch/decode하며, AudioContext 재개 대기와 부트를 결합하지 않는다. 미준비 SFX는 기존 lazy load/무음 폴백을 사용한다. 이는 Cold Start 임계경로를 줄이는 구조 변경이며, headless 테스트 캐릭터 전체 부트는 맵·청크·캐시 대기로 여전히 124초 제한을 초과했으므로 FPS 또는 전체 로드 시간 개선 수치를 아직 주장하지 않는다.

## 5. 잔존 이슈

### 5.1 첫 envVig 198ms (과거 1회성 측정, 2026-08-10 재검증)
- **성격**: Canvas2D radialGradient + drawImage 첫 빌드 비용
- **발생 시점**: 게임 첫 프레임에서 1회
- **실제 영향**: 게임플레이 중 절대 미발생. 사용자 체감 0
- **과거 가설 정정**: 현재 코드의 부트·렌더는 모두 `G._dvgCvs`를 사용한다. headless Chrome에서 `G._dvgStage===G.stage`, `G._dvgW===C.width`, `G._dvgCvs` 크기 일치를 확인했으므로 “캐시 객체 불일치”는 현 코드의 원인이 아니다.
- **현재 판정**: 실사용 Cold Start에서 첫 ProxyX GPU 제출 비용이 다시 재현되기 전까지 추가 웜업 코드를 넣지 않는다. 캐시 키는 정상이며, 과거 수치를 현재 병목으로 취급하지 않는다.
- **검증**: `tools/verify_env_vignette_warm_browser.mjs`.

### 5.2 첫 proj 그리기 46ms (1회성)
- **성격**: GPU 셰이더 JIT 컴파일 (linkProgram은 끝났으나 첫 drawElements 시점에 머신코드 생성)
- **발생 시점**: 첫 pProj 발사 시 1회
- **실제 영향**: 1프레임 끊김
- **미해결 사유**: 워밍업으로 부분 개선 (50ms → 46ms). 완전 제거는 `_glMainProg`에 실제 텍스처 바인딩 + 실제 픽셀 출력 필요
- **권장**: 무시

### 5.3 shieldQ 첫 오라 텍스처 업로드 (2026-08-10 해결)
- **원인**: 기존 `_wqCvs` 1×1 Canvas2D 워밍업은 ProxyX(WebGL2)가 실제로 사용하는 `_SA_IMG`·`_SA_IMG_R` 텍스처를 업로드하지 못했다. 첫 `sBlock` 오라 렌더에서 두 480×480 소스가 GPU에 처음 올라가며 스파이크가 발생했다.
- **수정**: `_WQ_SHIELD_AURA` 워밍업 항목이 `_warmShieldAuraGpu()`를 호출한다. 이 함수는 로딩/백그라운드 큐에서 실제 `X.drawImage(...)` 두 번과 `_flush()`를 수행하되, 화면 밖 좌표와 `globalAlpha=0`을 사용한다. 비동기 로드 완료가 게임 시작 뒤라면 `_scheduleGpuWarm()`이 유휴 시간에 실행하며, `_saWarmDone` 전에는 오라 스프라이트만 잠시 건너뛰므로 전투 중 업로드를 유발하지 않는다.
- **검증**: Chrome headless·SwiftShader에서 오라만 측정했다. 수정 전 첫 렌더 `56.3ms`, 수정 후 첫 렌더 `6.4ms`, 후속 3회 `0~0.1ms`였다. 워밍업 비용은 로딩 단계로 이동한다.
- **회귀 검증**: `test/shieldAuraWarmup.test.js`, `tools/verify_shield_q_render_browser.mjs`.

### 5.4 시작 보호막(bonfire) 첫 포스트 렌더 업로드 (2026-08-10 해결)
- **관측**: 실제 로그에서 시작 5초 보호막이 활성화된 첫 포스트 구간에 `bonfire:13.4ms`가 기록되었다. 이는 맵 스트리밍·카메라 이동과 별개다.
- **수정**: 지연 생성하던 `G._bonfireImg`를 부트 시점 `_BONFIRE_BARRIER_IMG`로 바꾸고, `_WQ_BONFIRE_BARRIER`가 실제 ProxyX `X.drawImage(..., -1, -1, 1, 1)`와 `_flush()`를 로딩 단계에서 수행한다. 늦은 로드는 `_scheduleGpuWarm()` 유휴 경로로 이관한다.
- **보장**: `_bonfireBarrierWarmDone` 전에는 시작 보호막 그림만 보류한다. 따라서 전투/이동 프레임에서 첫 GPU 업로드가 발생하지 않는다.
- **검증**: `test/bonfireBarrierWarmup.test.js`와 `tools/verify_shield_q_render_browser.mjs`에서 방패 Q·시작 보호막 두 전용 워밍업 완료를 확인한다.

### 5.5 플레이어 아틀라스 첫 S6 렌더 업로드 방지 (2026-08-10)
- **관측 근거**: `drawP S6`는 스킬 이펙트·플레이어 스프라이트·무기 렌더를 합친 구간이다. 일반 1×1 Canvas2D 워밍업은 `_atlasP_img`가 비동기로 준비되기 전이면 건너뛸 수 있으므로, 첫 플레이어 아틀라스 ProxyX 업로드가 이 구간의 1회성 스파이크 후보였다.
- **수정**: 아틀라스 JSON 로드 완료 시 `_queuePlayerAtlasGpuWarmup()`을 예약하고, 부트 워밍업 큐에도 `_WQ_PLAYER_ATLAS`를 넣는다. `_warmPlayerAtlasGpu()`는 화면 밖 1px 쿼드로 `_atlasP_img`를 실제 GPU 경로에 업로드한다. 로드가 게임 시작 뒤라면 `_scheduleGpuWarm()` 유휴 콜백이 먼저 업로드하고, `_playerAtlasGpuWarmDone` 전 S6는 기존 폴백 경로를 사용한다.
- **검증 범위**: `test/playerAtlasGpuWarmup.test.js`, `test/specialWarmupIdle.test.js`가 비동기 완료·유휴 예약·실제 ProxyX flush·S6 아틀라스 게이트 계약을 보장한다. S6의 세부 원인은 다음 실사용 로그에서 재확인한다.

### 5.6 S6 원인 분리 계측 (2026-08-10)
- **출력 조건**: `drawP` 총 시간 16ms 초과이면서 S6가 4ms 초과할 때 `[S6-SUB]`을 출력한다.
- **출력값**: `prePlayer`(S5 이후~플레이어 렌더 직전), `player`(플레이어 아틀라스/폴백 본체), `weapon+overlay`(플레이어 뒤쪽 렌더)를 각각 ms 단위로 분리한다.
- **목적**: 다음 재현 로그에서 선행 스킬 FX·플레이어 첫 아틀라스 업로드·무기/오버레이 렌더 가설을 구분한다. 이 변경은 측정 전용이며 최적화 판정 수치가 아니다.

### 5.7 이동 중 맵 드리프트/꿈틀거림 (2026-08-10 해결)
- **원인**: 스트리밍 뷰포트 캔버스는 과거 `_offX/_offY` 기준으로 합성하지만, WebGL2 경로가 현재 `_drawX/_drawY`에 그렸다. 재합성 간격도 3타일이어서 이동 중 캐시 내용과 월드 좌표가 어긋났다.
- **수정**: 항상 `_streamVpWorldX/Y`에 그리며, 2타일 여백을 넘기기 전에 1타일마다 재합성한다. 청크/맵 데이터와 게임플레이는 변경하지 않는다.
- **검증**: `test/mapStreamViewportOrigin.test.js`.

### 5.8 이동 중 청크 생성 히치 분리 계측 및 유휴 처리 (2026-08-10)
- **배경**: 초기 로그의 `[MAP STREAM] pre-built 1 chunks`는 부트 예산 안에 즉시 생성된 수가 적을 수 있음을 뜻한다. 남은 청크가 이동 중 큐에서 만들어질 때의 단일 청크 비용은 기존 전체 프레임 로그만으로 분리되지 않았다.
- **계측**: `_buildStreamChunk(cx, cy)` 한 번이 16ms를 넘을 때만 `[MAP STREAM SPIKE] <ms>ms chunk=<cx>,<cy> queued=<remaining>`을 출력한다.
- **수정**: `requestIdleCallback` 지원 브라우저에서는 플레이 루프가 청크를 직접 만들지 않고 `_scheduleStreamChunkBuild()`를 예약한다. 유휴 콜백 하나는 시간 예산 1~4ms 안에서 최대 1개만 생성하며 timeout에서도 1개로 제한한다. 지원하지 않는 환경은 기존 프레임 루프의 1~3개 폴백을 유지한다. 부트 로딩 화면의 준비 경로는 변경하지 않는다.
- **검증**: `test/mapStreamChunkSpikeDiagnostics.test.js`, `test/mapStreamIdleBuild.test.js`.

### 5.9 일반 아틀라스 실제 GPU 워밍업 (2026-08-10)
- **원인**: `_warmupEnsAtlas()`의 일반 이미지 경로는 과거 `_wqCtx` 오프스크린 Canvas2D에만 1px을 그렸다. 이 작업은 WebGL2 ProxyX/WebGPU가 사용할 텍스처를 확정 업로드하지 않으므로, 적·투사체·VFX 아틀라스의 첫 실전 `drawImage`가 남을 수 있었다.
- **수정**: 일반 큐 항목도 `_warmImageGpu(img)`에서 메인 렌더 컨텍스트 `X`에 화면 밖 투명 1px을 그린 뒤 `_flush()`한다. 큐는 기존처럼 `setTimeout(..., 0)`으로 한 장씩 처리하며, 특수 이미지의 준비 완료 게이트는 변경하지 않았다.
- **중복 제거**: 보호막 Q의 `_SA_IMG`·`_SA_IMG_R`는 `_WQ_SHIELD_AURA` 전용 항목이 이미 두 장을 함께 제출하므로 일반 큐에서는 제외했다.
- **일반 큐·지연 로드 처리**: `_wqGpuImages` Set은 게임 세션에서 실제 GPU 제출을 마친 이미지 객체를 기억하고, `_wqQueued` Set은 현재 패스의 중복이 80장 큐를 차지하지 않게 한다. 완료 뒤에도 적 렌더 구간이 180프레임(약 3초)마다 재검사하여 그 사이 로드된 새 이미지만 다음 유휴 큐에 넣는다. 임시 `_wqQueued`는 종료 시 해제한다.
- **플레이 중 잔여 처리**: 로딩 화면에서는 기존 `setTimeout(..., 0)` 체인을 유지하고, `G.on=true` 뒤 남은 다음 항목은 `requestIdleCallback(..., {timeout:120})`에서 한 장만 이어서 처리한다. 미지원 환경은 기존 setTimeout 폴백이다.
- **검증 한계**: 이 변경은 업로드 경로 계약을 정적으로 검증한다. 기기별 Cold Start 비용은 드라이버·이미지 크기에 따라 달라 실기기 프레임 시간은 별도 로그로 확인해야 한다.
- **회귀 검증**: `test/textureWarmupActualGpu.test.js`.

### 5.10 파티클 단일 프레임 스파이크 진단 (2026-08-10)
- **배경**: 기존 프레임 프로파일은 넓은 렌더 구간만 주기적으로 보여 주므로, 이동·전투 중 `poolRender()` 자체가 단일 프레임을 점유했는지 분리할 수 없었다.
- **계측**: `_DEBUG_PERF=true`일 때 가산 블렌딩 `poolRender()` 전후를 측정하고, 8ms 초과 프레임에서만 `[PART SPIKE] <ms>ms active=<활성 수> cap=<35 또는 80>`을 출력한다.
- **보장**: 파티클 렌더 상한은 코드 기준 PC 80개·모바일 35개이며, 이번 변경은 상한·스폰·VFX 외형을 변경하지 않는 진단 전용이다.
- **회귀 검증**: `test/particleSpikeDiagnostics.test.js`.

### 5.11 Cold Start 로딩 단계 계측 (2026-08-10)
- **배경**: 오디오 부트 대기를 비차단으로 바꾼 뒤에도 headless 테스트 캐릭터 경로가 124초 안에 `G.on=true`에 도달하지 않았다. 맵·청크·캐시 중 어느 대기인지 수치 없이 변경하면 원인을 잘못 고칠 위험이 있다.
- **계측**: URL `?perf=1`(또는 콘솔 수동 설정)으로 `_DEBUG_PERF=true`일 때 `showBootLoading()`이 기준점을 만들고, 모든 `setBootLoading(pct,msg)`가 직전 단계 대비 시간을 쌓는다. `hideBootLoading()`은 한 번만 `[BOOT PERF] total=<누적>ms | <진행률>% <단계>:<직전 단계 대비>ms ...`를 출력한다.
- **범위**: 로딩 UI가 닫히기까지의 시간만 측정한다. 그 뒤의 의도된 페이드·인트로 컷신 및 `G.on=true` 전환 대기는 이 로그 범위가 아니며, 로딩 순서·대기·렌더링은 변경하지 않는다.
- **회귀 검증**: `test/bootStageTimingDiagnostics.test.js`, `tools/verify_boot_stage_timing_browser.mjs`.

### 5.12 Cold Start 공통 에셋 개별 지연 분리 (2026-08-10)
- **실측**: Chrome headless·SwiftShader 표준 Cold Start 표본에서 `_preloadAssets()`의 첫 완료 이벤트가 약 1.47초, 로딩 화면 종료가 약 2.43초였다. 병렬 50여 장 묶음이므로 이 값만으로 특정 파일을 최적화하지 않는다.
- **계측**: `?perf=1`에서 각 이미지 요청의 시작~완료 시간을 계산하고 500ms 초과 파일만 `[BOOT ASSET SLOW] <ms>ms src=<경로>`로 출력한다.
- **보장**: 이미지 목록·요청 순서·15초 타임아웃·표현은 유지한다. 이 단계는 진단 전용이며, 반복적으로 느린 파일이 관측될 때만 후속 변경을 검토한다.
- **회귀 검증**: `test/bootAssetSlowDiagnostics.test.js`, `tools/verify_boot_stage_timing_browser.mjs`.
- **첫 판정**: Chrome headless·SwiftShader에서 거의 모든 항목이 1.43~2.38초로 함께 기록됐다. 이 값은 병렬 요청의 대기열을 포함하므로 특정 파일 결함이 아니다. 에셋 축소·삭제·임의 지연 로딩은 적용하지 않으며, Cold Start 완료 뒤의 이동 프레임 문제는 별도 실사용 프레임 로그로 계속 판단한다.

### 5.13 프레임 스파이크 콘솔 출력 게이트 (2026-08-10)
- **원인 후보**: 기존 `[drawP]`·S6/S7 상세·`[POST SPIKE]`는 이미 16ms를 넘긴 프레임에서 기본적으로 콘솔에 출력됐다. DevTools가 열린 개발/실사용 테스트에서는 포맷·출력 비용이 다음 프레임의 체감을 악화시킬 수 있다.
- **수정**: 위 프레임 스파이크 진단은 `_DEBUG_PERF=true`에서만 출력한다. URL `?perf=1`로 의도적으로 켜면 같은 상세 로그를 계속 얻는다.
- **보장**: 측정값·렌더 순서·VFX·맵·게임플레이는 변경하지 않는다. 일반 실행에서는 콘솔 호출만 제거한다.
- **회귀 검증**: `test/frameSpikeDiagnosticDebugGate.test.js`, `test/drawPS6Breakdown.test.js`.

### 5.14 전체 프레임 간격 히치 진단 (2026-08-10)
- **배경**: 루프는 `frameTime`을 50ms로 클램프해 물리 폭주를 막지만, 그 이전의 실제 rAF 간격이 기록되지 않아 브라우저 스케줄링/GC/업데이트/렌더 중 어느 쪽의 지연인지 첫 구분이 어려웠다.
- **계측**: `?perf=1`에서 원시 간격 34ms 초과 시 최대 500ms마다 `[FRAME HITCH] gap=<ms> U=<직전 update EMA> D=<직전 draw EMA> chunkQ=<청크 대기> warmQ=<워밍업 대기>`를 출력한다.
- **보장**: 기존 50ms 물리 클램프와 루프 순서를 유지한다. 일반 실행에는 비교·문자열 생성·콘솔 호출이 없다.
- **회귀 검증**: `test/frameHitchGapDiagnostics.test.js`.

### 5.15 브라우저 Long Task 분리 진단 (2026-08-10)
- **목적**: rAF 간격만으로는 게임의 update/draw 외에 GC·동기 브라우저 작업·외부 스크립트가 메인 스레드를 점유했는지 분리할 수 없다.
- **계측**: `?perf=1`에서만 `PerformanceObserver({type:'longtask', buffered:true})`를 한 번 연결해 50ms 이상 항목을 `[LONG TASK] <ms>ms`로 출력한다.
- **보장**: 미지원/등록 실패 환경은 조용히 생략하며, 일반 실행은 observer와 콜백을 생성하지 않는다. 게임 업데이트·렌더 경로는 변경하지 않는다.
- **회귀 검증**: `test/longTaskDiagnostics.test.js`.
