이동 중에는 프레임 루프 끝에서 청크를 동기 생성하면, 한 청크의 Canvas 구성 시간이 해당 조작 프레임에 그대로 더해진다. `requestIdleCallback`을 지원하는 브라우저는 `_scheduleStreamChunkBuild()`가 **유휴 콜백당 최대 1개**만 `_tickStreamChunkBuild()`로 넘긴다.

| 게임 플레이 + `requestIdleCallback` 지원 | 1개 | `timeRemaining()-1`을 1~4ms로 제한, timeout 시 1ms | 조작 프레임에서 Canvas 청크 생성 분리 |

## 정적 파일 스트리밍 Range 안정화 (2026-04-14)

2026-09-09 Steam 패키지 서버 `node-main.js`에도 단일 바이트 Range를 구현했다. `bytes=start-end`/`bytes=start-`/`bytes=-suffix`는 206·Content-Range·Content-Length·Accept-Ranges로 응답하며 종료 바이트는 파일 끝으로 제한한다. 잘못된 구간은 416, HEAD는 본문 없이 헤더만 반환, 연결 종료 시 스트림을 해제한다. 일반 정적 응답은 Content-Length/Accept-Ranges를 명시하고 HTML만 no-cache/no-store/must-revalidate를 적용한다. v13 컷 이동 실패를 재현한 뒤 패키지 인트로 회귀 PASS. [배포 기록](../13출시·마케팅/STEAM_LATEST_DEPLOY_20260909.md).

`server.cjs` 비디오/오디오 스트리밍 경로(`/video/`, `/sfx/`, `/bgm/`)에서 브라우저 Range 요청 안정화.

| 항목 | 변경 전 | 변경 후 |
|------|---------|---------|
| Range start 파싱 | `parseInt(parts[0],10)` | `parseInt(parts[0],10) \|\| 0` (비정상 값 방어) |
| Range end 상한 | 요청값 그대로 사용 | `Math.min(end, stat.size-1)` |
| 잘못된 구간 처리 | 예외 가능 | `416 Range Not Satisfiable` + `Content-Range: bytes */size` |
| 스트림 에러 핸들링 | 없음 | `createReadStream(...).on('error', ...)`로 500 응답 안전 처리 |

| `_scheduleWarmupNext()` | 로딩 중 `setTimeout(fn,0)` 체인, 게임 시작 뒤 `requestIdleCallback(..., {timeout:120})`로 다음 1장 예약 |
| `_scheduleGpuWarm()` | 비동기 완료된 Q 오라·시작 보호막·플레이어 아틀라스 전용 업로드를 로딩 중 즉시, 플레이 중 유휴 시간에 예약 |
| `_warmImageGpu(img)` | 화면 밖 1px·`globalAlpha=0`으로 `X.drawImage` 후 `_flush()`; 렌더 상태를 저장/복원 |
| `_wqGpuImages` | 게임 세션 동안 실제 GPU 제출을 마친 이미지 객체 `Set`; 재검사·스테이지 전환에서도 같은 이미지는 다시 제출하지 않음 |
| `_wqQueued` | 현재 워밍업 패스의 임시 `Set`; 같은 이미지가 여러 수집 경로에 있어도 큐 칸을 1개만 사용하고 완료 시 해제 |
| `_WQ_SHIELD_AURA` | Q 보호막 480×480 파란·빨간 시트 전용 항목. `_warmShieldAuraGpu()`가 실제 ProxyX `X.drawImage` 2회와 `_flush()`로 GPU 텍스처 업로드를 로딩 중 완료. 두 시트는 일반 큐에 중복 적재하지 않음 |
| `_WQ_BONFIRE_BARRIER` | 시작 5초 보호막 `sprites/bonfire_barrier.png` 전용 항목. `_warmBonfireBarrierGpu()`가 실제 ProxyX에서 화면 밖 1px 쿼드를 flush해 첫 포스트 렌더 업로드를 로딩 중 완료 |
| `_WQ_PLAYER_ATLAS` | 비동기로 준비되는 **외부 Image 기반** `_atlasP_img` 전용 항목. `_warmPlayerAtlasGpu()`가 실제 ProxyX에서 화면 밖 1px 쿼드를 flush해 플레이어의 첫 스프라이트 렌더 업로드를 로딩 중 완료. 캐릭터 선택 8방향 PNG를 조립한 Canvas 아틀라스는 이 항목의 대상이 아님 |

| 호출 시점 | 설명 |
|-----------|------|
| 부트 완료 (`_dbReady=true` 직후) | 큐 적재 + setTimeout 체인 시작 |
| ens 렌더 루프 진입 | 미완료 시 `_warmupEnsAtlas()` 재시도 (지연 로드 커버) |
| `nextStage()` | `_ensWarmDone=false` 리셋 → 다음 렌더 시 재적재 |

워밍업 대상은 로드 완료 상태에 따라 가변(일반적으로 수십 장)이며, 8dir idle/walk, 보스·구울·투사체·플레이어 스프라이트와 추가 VFX 텍스처를 포함한다. 일반 이미지 적재 상한은 80장이다.

일반 큐는 전용 항목 다음에 공용 전투 텍스처를 먼저 수집하며, `_queueWarmImage()`가 현재 패스의 중복 및 이미 GPU에 올린 이미지를 먼저 제외한다. 따라서 중복이 80장 상한을 점유하지 않고, 늦게 로드된 새 이미지만 다음 패스에 들어간다. `_wqQueued`는 종료 시 비우며, `_wqGpuImages`는 같은 GPU 컨텍스트를 쓰는 게임 세션 동안 유지한다. 로딩 화면을 넘겨 남은 항목은 `G.on=true` 후 브라우저 유휴 시간에 한 장씩 처리하므로 조작 프레임의 GPU 업로드 경쟁을 줄인다.

적 렌더 구간은 워밍업 완료 뒤에도 180프레임마다(60fps 기준 약 3초) 한 번만 가볍게 재검사한다. 이미 준비된 이미지는 Set 조회만 하고, 그 사이 로드 완료된 이미지가 있을 때만 새 유휴 큐를 시작한다.

일반 워밍업도 `_warmImageGpu()`를 통해 ProxyX(WebGL2)/WebGPU의 실제 텍스처 업로드까지 완료한다. 보호막 Q·시작 보호막·플레이어 아틀라스는 비동기 준비 완료와 렌더 보류 상태가 따로 필요하므로 전용 GPU 워밍업 항목을 유지한다. `_saWarmDone`이 되기 전에는 오라 스프라이트 렌더를 보류하여 플레이 중 첫 사용 프레임에 업로드가 발생하지 않게 한다.

시작 보호막도 `_bonfireBarrierWarmDone` 전에는 스프라이트를 보류한다. 이 구간은 시작 직후 무적 보호막의 시각 효과뿐이며, 준비가 끝난 다음 프레임부터 정상 표시된다. 따라서 첫 포스트 렌더에서 `bonfire`가 텍스처 업로드를 수행하지 않는다.

외부 Image 기반 플레이어 아틀라스는 `_playerAtlasGpuWarmDone` 전까지 기존 폴백 렌더 경로를 사용한다. 비동기 아틀라스 로드 완료 직후의 첫 S6 프레임이 GPU 업로드를 대신 수행하지 않고, `_scheduleGpuWarm()`이 완료한 뒤부터 아틀라스 렌더로 전환한다. 반면 캐릭터 선택 PNG 8장을 `_load8Dir()`가 조립한 Canvas 아틀라스(`_atlasP_img.getContext` 존재)는 기본 아틀라스의 워밍 플래그를 공유하지 않고 `_atlasPReady` 즉시 렌더한다. 따라서 실버테일처럼 준비 완료된 선택 캐릭터가 무관한 기본 PNG 워밍 지연 때문에 절차적 외눈 폴백에 남지 않는다.

### URL 공유 텍스처 + 학습형 비동기 프리워밍 (2026-10-01, PM-001)

위 목록형 워밍업은 열거한 이미지만 올린다. 열거되지 않은 큰 스킬·드롭 시트는 첫 사용 프레임에 `texImage2D(Image)`가 디코드까지 동기 수행해 11~79ms씩 멈췄다(전투 첫 20초 합계 462~605ms 실측). 2026-10-01부터 `_getTex`는 같은 URL의 텍스처를 `_texBySrc`로 공유하고, 이전 세션에 동기 업로드가 발생했던 큰 이미지(`localStorage hell_texhot_v1`, 최대 96개·64MP)와 기본 시드 22개를 `fetch→Blob→createImageBitmap(premultiplyAlpha:'none')`로 메인 스레드 밖에서 디코드해 프레임말에 1장씩 올린다. 픽셀 동일·기존 동기 폴백 유지·WebGL2 전용. `_warmupEnsAtlas()` 첫 줄이 `_texPrewarmHot()`을 호출하고 `loop()`가 `_texPreDrain()`을 호출한다. 상수·함수·한계·검증은 [TEXTURE_ASYNC_PREWARM_20261001.md](TEXTURE_ASYNC_PREWARM_20261001.md).

## 500마리 난전 디버그 프로파일러 (`_PERF_PROF`, 2026-04-17 추가)

게임 메인 루프(`function loop`) 내부에 주입된 측정 전용 코드. **기존 게임 로직은 일절 수정하지 않음** — 호출부만 감싸고 일부 함수는 외부에서 참조 교체로 후킹.

### 활성화 조건
- `?perf=1` 또는 `G.debugPerf=true`이고 활성 몹 수(`ens`에서 `alive===true`)가 **300 초과**일 때 ON
- 일반 플레이에서는 `_perfFrameTick()`이 즉시 반환하여 적 수 스캔과 GL/Canvas 후킹을 설치하지 않음 (2026-09-27)
- 300 이하로 떨어지면 자동 OFF (오버헤드 회피)
- ON/OFF 시 콘솔에 `[PERF] ON (enemies=N)` / `[PERF] OFF (enemies=N)` 로그

### 측정 구간 (4종)
| 키 | 측정 대상 | 후킹 방식 |
|---|---|---|
| `ai` | `update()` while 루프 전체 시간 − `coll`. AI/이동/스킬/플로우필드 등 게임 로직 | 루프 내 호출부 감싸기 (`_aiAcc`) |
| `coll` | `_applyColResult()` + `_dispatchColWorker()` (충돌 워커 디스패치/결과적용) | 함수 참조 교체 (외부 후킹) — update 내부 무수정 |
| `render` | `draw()` 호출 (보간 분기 포함) | 루프 내 호출부 감싸기 (`_renderAcc`) |
| `dom` | `_fpsDraw()` + `_glFlush()` + `_drawBurst()` (포스트렌더 UI/GPU flush) | 루프 내 호출부 감싸기 (`_domAcc`) |

### 출력
- **60프레임마다** 콘솔에 한 줄:
  ```
  [PERF] enemies=487 drawCalls=18 ai(avg/max)=4.2/6.8ms coll=8.7/12.1ms render=3.1/4.5ms dom=2.3/3.0ms heap=245MB
  ```
- 각 구간 `avg/max` 60프레임 윈도우 (롤링 큐)
- `drawCalls` = WebGL `drawArrays`+`drawElements` 호출 횟수 (**enabled 프레임 30개** 누적, 출력 후 리셋 — OFF 프레임은 카운트 안 함, 아래 Track B 참조)
- `heap` = `performance.memory.usedJSHeapSize` MB (Chromium 전용)

### 데이터 구조
```js
const _PERF_PROF={
  enabled:false, frameCnt:0,
  ai:[], coll:[], render:[], dom:[], drawCalls:0,        // 윈도우 + 카운터
  _aiAcc:0, _collAcc:0, _renderAcc:0, _domAcc:0,         // 프레임별 누산기 (tick 끝에 리셋)
  _hooked:false, _origACR:null, _origDCW:null            // 후킹 백업 참조
};
```

### 8방향 적 GPU 배치 보조 로그 (2026-08-09)

`_DEBUG_PERF=true`일 때 기존 30프레임 진단 로그에 `e8:인스턴스수@버킷드로우수`가 함께 출력된다.

```
[PERF] ... ens:2.1 e8:500@8 proj:1.4 ...
```

- 앞 수(`500`): 해당 프레임 WebGL2로 그린 8방향 idle/walk 스프라이트 인스턴스 수
- 뒤 수(`8`): 실제 활성 텍스처 버킷의 `drawArraysInstanced` 호출 수. idle 8방향 + walk 8방향이므로 최대 16
- 이 값은 `_PERF_PROF`의 30프레임 누적 `drawCalls`와 목적이 다르며, 8방향 배치가 Canvas 폴백 없이 합쳐졌는지 빠르게 확인하는 진단값이다.

### 후킹 함수
- `_perfHookGL()` — 1회만 실행. WebGL 드로우콜 카운터 + `_applyColResult`/`_dispatchColWorker` 함수 교체. 원본은 `_origACR`/`_origDCW`에 보관.
- `_perfFrameTick()` — 매 프레임 마지막에 호출. 디버그 모드에서만 활성 몹 카운트 → ON/OFF 토글 → 누산값을 윈도우에 push → 60프레임마다 `_perfReport()`.
- `_perfReport()` — 콘솔 출력. 빈 배열 시 `'0.0/0.0'`.

### 주의
- 일반 플레이에서는 후킹 자체를 설치하지 않는다. 디버그 모드에서 몹 ≤ 300이면 래퍼의 카운터 증가를 `if(_PERF_PROF.enabled?...:0)` 가드로 건너뛴다.
- 충돌 후킹은 `_PERF_PROF.enabled` 체크 후에만 누산 (OFF 시 패스스루)
- update 내부의 인라인 충돌 검사(투사체↔적, 플레이어↔적)는 측정 안 됨 — `ai` 항목에 포함됨

### Track B 종결: `drawCalls` 윈도우 회계 결함 (2026-08-16, VERDICT=B3)

**증상**: `_PERF_PROF` 리포트가 `drawCalls:2,775,741`을 30프레임 창으로 출력 → 92,525 draws/frame으로 오해. 이를 "렌더 폭주"로 간주해 여러 트랙(맵 캐시 miss, texture setter, MAP_OBJS cardinality, enemy/proj/particle)을 조사했으나 전부 배제됨.

**근본 원인 (B3 = WINDOW ACCOUNTING ERROR, 카운터 배수 결함 아님)**:
- `_perfHookGL()`의 `drawArrays`/`drawElements` 래퍼가 **`enabled` 가드 없이** 무조건 `drawCalls++` 했음 (C2D 래퍼는 가드 있었음 — 불일치). 위 "주의" 항목이 *모든* wrapping에 가드가 있다고 서술했으나 실제 GL 드로우 래퍼만 예외였다.
- `frameCnt`는 `enabled` 프레임에서만 증가(`frameCnt%30===0` 리포트).
- 시나리오: 몹>300 → ON(훅 설치) → 몹≤300으로 하락 → OFF(`drawCalls=0` 리셋) → **OFF 구간 수천 프레임 동안 래퍼가 계속 draw 누적** → 몹>300 재상승 → ON(리셋 없음, 잔여 누적 carry) → 30 enabled 프레임 후 리포트가 (OFF 갭 draws + 30프레임)을 "30프레임"으로 출력.
- OFF 갭이 수십 초(수천 프레임)면 평시 draw/frame(수백~수천) × 프레임수 = 수백만 → 2.7M은 이 범위에 정확히 부합.

**검증 (독립 probe, `tmp/probe_perf_profiler.py` + `probe_trackb_confirm.py`)**:
- 카운터 무결성: 실제 N draw → counter 정확히 N. context lost/restored 3회 반복 후에도 37→37 (Chrome은 `WebGLRenderingContext` 객체를 restore 시 재사용 → `__perfHooked` 유지 → 래퍼 중첩 없음). **배수 결함(B2) 반증.**
- 윈도우 결함 재현: OFF 상태 19 draw → `disabledDelta=19`, 재-ON 첫 리포트 `reported=19` (팬텀 누출 확인).
- 실제 최대 프레임 부하(`_DCP`, stage 2 = 185 오브젝트/22 visible): **dc=45** draws/frame. 92,525/frame은 물리적으로 불가능 → 2.7M은 반드시 다중 윈도우 누적.
- 렌더 진입 재진입 없음: `raf=1 main=1 draw=1 map=1 world=1 entity=1 post=1` (프레임당 정확히 1회). `draw()`는 `if(_didUpdate&&G.cam){draw()}else{draw()}` 단일 호출, `requestAnimationFrame(loop)` 5개 사이트 전부 상호배타 early-return, `_startLoop` `_looping` 가드로 멱등.
- source attribution: `sourceSum === dc`, `unknown=0` 항상 성립.

**수정 (instrumentation-only, 게임플레이 무영향)**:
- `drawArrays`/`drawElements` 래퍼에 `if(_PERF_PROF.enabled)` 가드 추가 (C2D 래퍼와 동일). → OFF 프레임 카운트 차단.
- ON 진입 시 `drawCalls=0` 리셋 추가 (`_perfFrameTick`) — 이전 잔여 격리(방어적).
- 수정 후 검증: OFF draw → `disabledCount=0`, 재-ON 리포트 `reported=0`, ON draw 41 → `enabledCount=41` (정상 카운트 유지).

**결론**: 실제 draw-call runaway는 존재하지 않았다. "90K 트리거"는 계측 창 회계 결함이 만든 팬텀. production 렌더 경로는 정상(최대 ~45 draws/frame). Track B **CLOSED**.

## §6.13 Performance Regression Budget Gate (2026-08-15)

**성격**: 최적화 아님 — 회귀 감지/방지 전용. PERF OPTIMIZATION TRACK은 CLOSED 상태 유지.
향후 gameplay/content 변경이 확보한 headroom을 깨뜨리는지 반자동 감지하는 최소 외부 harness.

**파일**: `tools/perf_regression_gate.mjs` (외부 Playwright harness) + `tools/perf_baseline.json` (known-good baseline).
game.html에 **permanent profiler/counter 무추가** — 외부 rAF 프로브(`window.__fp`)를 페이지에 주입해 raw frame dt 수집. `_prof`(기존 EMA)와 `?perf=1`(기존 진단 게이트)만 재사용. 진단 코드가 production default path에 남지 않음.

### 사용법
```
node server.cjs                                      # 포트 3333 (필수)
node tools/perf_regression_gate.mjs                  # 1회 리포트
node tools/perf_regression_gate.mjs --baseline --runs=3   # N회 측정→median/range 저장
node tools/perf_regression_gate.mjs --check          # baseline 대비 상대 회귀 advisory
```
HEADED 실GPU 필수(headless swiftshader는 수백 엔티티에서 crash/document.hidden sim정지). CI hard gate 부적합.

### 시나리오 (기존 실 gameplay path 우선)
| ID | 이름 | 적 | 스킬 | pProj cap | 목적 |
|---|---|---|---|---|---|
| A | STEADY_COMBAT | 300 | 없음 | — | 일반 교전 draw/AI bound |
| B | SKILL_BURST | 150 | iceOrb·venomBlade·maliceHunt·bladeShard | 80 | 기존 SFX regression 부하 |
| C | HOMING_STRESS | 300 | maliceHunt·plagueBurst | 60 | plagueHoming/mhBlade 관통·재획득 |

### 기록 metric
frame dt p50/p95/p99/max, dt>16.7 count, dt>33 count, FPS(참고), U/D/T EMA(p95 근사), scenario duration, enemy/pProj workload count, cast count.

### Baseline variance (2026-08-15, 동일 PC 3회)
| Scenario | dt_p50 spread | dt_p95 spread | dt_p99 spread | fps spread | 판정 |
|---|---|---|---|---|---|
| **A** STEADY_COMBAT | **0%** (4.2/4.2/4.2) | **2.3%** | 50% | 11% | **신뢰센서** |
| B SKILL_BURST | — | 13.9% | 109% | 23% | diagnostic-only |
| C HOMING_STRESS | — | 55.8% | 97% | 87% | diagnostic-only |

- **A의 central metric(p50/p95)만 극안정** → 유일한 FLAG 대상.
- B/C는 pProj를 대표화(cap)해도 forced-dispatch cadence(≈8casts/s vs 실 1~2/s)가 VFX/particle 부하를 과구동 → fps/p99 spread 23~109%. **본질적으로 artificial**이라 hard 센서 부적합.
- A의 tail(p99/max/hitch)도 one-off GC/settle spike로 노이즈(hitch spread 1000%+) → 표시만.

### Gate 설계 (relative, advisory-only)
- **FLAG 대상 = `A.dt_p50`, `A.dt_p95`뿐**. 나머지(A tail·B·C 전량)는 info(δ 표시, 무플래그).
- Threshold = 관측 spread 위 floor 25%p + 10%p 마진 (임의 5/10% 아님, A 노이즈 ≤2.3% 대비 넉넉).
- fps는 부호 반전(낮을수록 악화).
- **항상 exit 0** — correctness CI(test/ deterministic guard)를 절대 안 깸. perf는 advisory로 완전 분리.
- 자기일관성 검증: 동일 빌드 재측정 시 B.dt_p99가 +59.6% 튀어도 info로만 표기, A 신뢰센서는 Δ0.0%/−2.3%로 무플래그 → false-positive 0 확인.

### REOPEN CONDITION 연결
`--check`의 A 신뢰센서 FLAG = REOPEN 후보 신호. 세 조건(①재현 user-visible hitch ②material FPS/p95/p99 regression ③신규 workload가 headroom 소비) 중 ②를 steady-state에서 자동 감지. B/C 리포트는 skill/homing 축의 참고 지표(수동 재현 확인용).

- **AUTOMATION RELIABILITY**: A steady-state = 신뢰(hard-ish advisory 가능). B/C = too flaky → diagnostic-only. Hard CI gate 금지 유지.
